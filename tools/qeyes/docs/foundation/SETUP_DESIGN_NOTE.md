# 準備内容を生成するための設計書について

設計書は「アプリそのものの設計」ではなく、「アプリを作れる状態をどう整えるかの設計」に分けるのがよいです。つまり実装対象は `qeyes` ではなく、`qeyes` を継続的に作れる開発基盤です。

おすすめは 1 枚に全部詰めず、次の 3 層で分ける形です。

## 1. 目的と範囲の設計書

名前の例:

- `docs/foundation/FOUNDATION_DESIGN.md`

書く内容:

- 何の準備を対象にするか
- どこまでを「準備完了」とみなすか
- 何をこの設計書の対象外にするか

例:

- 実装方針
- 文書方針
- リソース方針
- リリース方針
- テンプレート
- ルール文書
- 対象外
- 実際の機能設計詳細
- UI の細部仕様

## 2. 成果物一覧の設計書

名前の例:

- `docs/foundation/DELIVERABLES.md`

書く内容:

- 準備によって何が生成・整備されるか
- 各ファイルの役割
- 相互参照

例:

- `AGENTS.md`
- `README.md`
- `docs/README.md`
- `docs/history/RELEASE_HISTORY.md`
- `docs/guides/USER_GUIDE-<version>.md`
- `docs/releases/ReleaseNote-<version>.md`
- テンプレート類

これがあると、「準備の完了条件」が見えやすいです。

## 3. 更新ルールの設計書

名前の例:

- `docs/foundation/MAINTENANCE_RULES.md`

書く内容:

- 新バージョン時に何を更新するか
- 新文書種別追加時に何を更新するか
- README と docs README の役割分担
- ルール変更時の反映先

これは今 `AGENTS.md` に一部入っていますが、設計書としては別にまとめた方が読みやすいです。

## 推奨構成

```text
docs/
  foundation/
    FOUNDATION_DESIGN.md
    DELIVERABLES.md
    MAINTENANCE_RULES.md
```

## 設計書に最低限入れるべき観点

- 目的
- 完了条件
- 成果物一覧
- 命名規則
- 更新規則
- 役割分担
- 例外処理
- 将来拡張方針

特に重要なのは「完了条件」です。

今回で言うと、例えば次のように書けます。

- `AGENTS.md` が存在する
- 実装方針、文書方針、リソース方針が定義されている
- ルート `README.md` が存在する
- `docs/README.md` が存在する
- 版付き利用ガイドと版付きリリースノートのテンプレートが存在する
- リリース履歴ファイルが存在する

この形にすると、設計書が単なる説明ではなく、チェック可能な仕様になります。

## 実務上さらに重要な点

- 判断表
  - 何が増えたときに何を更新するか
- 非目標
  - 何はこの基盤設計の責任外か

例えば判断表です。

- 既存種別の文書追加
  - `RELEASE_HISTORY.md`
- 新文書種別追加
  - `docs/README.md`, `AGENTS.md`
- 利用者向け主要文書追加
  - `README.md`
- 命名規則変更
  - `AGENTS.md`, テンプレート

## 結論

設計書は次の方針で作るのがよいです。

- 1枚に全部書かない
- 「目的」「成果物」「更新規則」を分ける
- 完了条件を明文化する
- 判断表を入れる
