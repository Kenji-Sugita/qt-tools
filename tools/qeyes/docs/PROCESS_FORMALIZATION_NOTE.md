# 開発工程の形式化について

今回のような開発工程の形式化は妥当です。

ただし、妥当なのは「この規模に合わせて軽く形式化する」場合です。

今回の流れはこう整理できます。

- 要望書
- 要件定義
- 概要設計
- 詳細設計
- 開発基盤設計

これは古典的な工程をそのまま重く持ち込んだのではなく、小規模プロジェクト向けに縮約した形なので、不自然ではありません。

## 妥当な理由

- 後から見て、なぜ作ったかが分かる
- 要件と実装の対応が追いやすい
- 文書追加や版更新の判断がしやすい
- AI や他人が入っても迷いにくい
- 小さな変更でも、どの層の話か整理できる

## 注意点

- 文書が増えすぎると保守コストが上がる
- 実装より文書更新が重くなると逆効果
- 小変更でも全工程を更新しようとすると過剰運用になる

したがって、妥当かどうかは「全部あること」ではなく、「重さが適切かどうか」です。

## 今回の `qeyes` で妥当な点

- 文書は短め
- 層ごとの役割が分かれている
- 詳細を全部書き切ろうとしていない
- 更新ルールも明文化されている

つまり、今の形は「小規模でも使える軽量な形式化」としてかなり妥当です。

## 実務上の評価

- 大規模案件の正式工程としては軽い
- 個人開発や小規模ツールとしては十分に整理されている
- AI と協調して進める前提では、むしろ有効

## 結論

- 今回のような形式化は妥当
- ただし今後も「必要なときだけ更新する」運用を守るのが前提
- 過剰に厳密化し始めたら見直すべき
