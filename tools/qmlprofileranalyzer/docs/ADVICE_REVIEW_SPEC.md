# Advice Review Spec

## 目的

`advice.txt` で指摘された QML Profiler 解析上の論点を、`qmlprofileranalyzer` の今後の仕様候補として整理する。

この文書の目的は実装ではなく、次の判断材料を揃えることにある。

- 何をツール機能として実装するか
- 何を運用ガイドとして扱うか
- 何を推定表示に留めるか
- 何を今回の対象外にするか

## 前提

- 現行 CLI は単一トレースを読み、`summary`, `types`, `events`, `events-aggregated`, `notes` を出力する
- 現行の集計は主に `count`, `totalDuration`, `maxDuration` ベースである
- `qtd` / `qzt` には `self time` は一次情報として格納されていない
- `self time` や親子関係は range の時系列と入れ子構造から復元する必要がある

## advice.txt の論点整理

### 1. 計測条件の妥当性

対象操作だけを抽出したログが望ましい。
常時アニメーションなどのノイズ源は、必要に応じて停止した状態で計測する。

扱い:

- ツール実装ではなく運用ガイド
- 将来的に時間範囲フィルタがあれば補助できる

### 2. 初回と再訪時の分離

画面遷移系では、初回と 2 回目以降を分けて複数ログで比較したい。

扱い:

- 単一トレース内分析だけでは不十分
- ツール機能としては当面対象外
- 運用ガイドで比較手順を補う

### 3. Compiling の解釈

初回の大きい `Compiling` は大規模 QML の兆候になりやすい。
一方で、`import` に伴うプラグイン検索やロードは見えない負荷になることがある。

扱い:

- 実測値そのものは出せる
- 原因の断定は避ける
- レポートでは注意表示または解釈ガイドを付ける

### 4. 初回生成時の画像・フォント影響

初回の画面生成では画像やフォント処理が支配的な場合がある。

扱い:

- `PixmapCache` など観測可能なイベントは補助材料として使える
- フォント処理は常に直接観測できるとは限らない
- 原因候補の提示に留める

### 5. Creating / Binding の親子関係

`Creating` や `Binding` は親子関係を考慮しないと、同じ処理を複数箇所で重複評価してしまう。

samegame の例では、親子関係が分かれば実際に着目すべきノードは限定される。

扱い:

- 今回の最重要項目
- 親子関係の復元と `self time` 算出が必要

### 6. self time の必要性

`self time` の確認は必須だが、トレース形式には直接含まれない。
range をもとに関係性を復元して算出する必要がある。

扱い:

- 今回の最重要項目
- `inclusive time` と `self time` を分けて表示する

### 7. 親の空き領域

`Compiling` 以外の大きめの親 range の内部に大きな空き領域がある場合、JavaScript や C++ 側処理の可能性がある。
ただし、QML イベントが発生しない処理はトレースだけでは断定できず、ソース確認が必要である。

扱い:

- 差分値は算出できる
- 原因は推定表示に留める

### 8. ListView / Repeater のバースト

`ListView` や `Repeater` 起因のバースト的な `Creating` 群は重要である。
`Calls(count)` はその判定材料になりうる。

扱い:

- 実装候補
- 件数と短時間集中の見せ方を検討する

### 9. 外れ値

一つだけ長いイベントなど、統計的な外れ値はノイズか実害かの見極めが必要である。

扱い:

- 実装候補
- 平均だけでなく `min/max` や分位点などの分布指標を検討する

### 10. 平均値の落とし穴

`Calls = 2` で片方だけ極端に長い場合、平均値は実態をぼかす。

扱い:

- 実装候補
- 平均を主指標にしないか、補助指標に下げる

### 11. UI 遷移時間の定義

画面遷移時間は、UI 観点ではボタン押下の release から一連の描画完了までである。
アニメーションが絡むと複数回描画になり、ツール側の自動検出は難しい。

扱い:

- 高難度機能
- 直近の対象外候補

## 仕様方針

### 基本方針

- まず単一トレース内で完結する分析強化を優先する
- 親子関係を要する分析と、運用上の注意事項を分離して扱う
- 原因を断定できないものは、推定または注意表示として出す
- 既存 `summary` を壊さず、必要なら新コマンドを追加する

### 直近で仕様化する対象

1. range 親子関係の復元
2. `self time` 算出
3. `inclusive time` と `self time` の分離表示
4. 親子重複を避けるための着目ノード表示
5. `count` に加えて `min/max` など分布の基本指標を追加
6. 外れ値候補の明示
7. バースト候補の明示
8. 親内部ギャップの可視化

## 優先順位

優先順位は次の基準で付ける。

1. 現行出力の誤誘導をどれだけ減らせるか
2. `advice.txt` の中核要求にどれだけ直接応えるか
3. 単一トレース内で完結して実装できるか
4. 既存 CLI への影響を抑えつつ段階導入できるか

### Priority 1

- range 親子関係の復元
- `self time` 算出
- `inclusive time` と `self time` の分離表示
- `ranges` コマンド追加

理由:

- `advice.txt` の中心指摘である `Creating` / `Binding` の親子重複問題に直接対応するため
- 現行の `totalDuration` 主体の見え方で起きる誤誘導を最も大きく減らせるため
- samegame 例のような「同じ処理を複数箇所で重く見せてしまう問題」をまず解消すべきため

### Priority 2

- 親子重複を避けるための着目ノード表示
- 親内部ギャップの可視化
- `summary` への注意表示追加

理由:

- Priority 1 の結果を利用して、読み手がどこを見るべきかを判断しやすくする段階だから
- 親子関係の復元前に実装しても精度が不足するため
- QML 外処理の可能性や `summary` の読み方を補助できるが、基礎計算より後でよいため

### Priority 3

- `count`, `min/max`, `median` など分布の基本指標
- 外れ値候補の明示
- `hotspots` コマンド追加

理由:

- 平均値の落とし穴や外れ値問題への対応として重要だが、まず `self time` を持った基盤が必要なため
- 集約ロジックは基礎データが正しくなってから載せた方が仕様がぶれにくいため

### Priority 4

- バースト候補の明示
- 画像影響の補助表示強化
- `Compiling` 解釈への注意表示

理由:

- 有用ではあるが、主要な誤誘導要因そのものではなく補助的な解釈支援だから
- 画像影響や `Compiling` 解釈は推定表示の性質が強く、基礎分析より優先度は下がるため
- バースト検出はルール設計に裁量が入りやすく、土台完成後の方が詰めやすいため

### 運用ガイドで扱う項目

- 初回トレースと再訪トレースの比較
- 同一操作の複数回測定条件の揃え方

理由:

- 単一トレース解析を超えると、入力条件の統制と差分解釈の難しさが急に増えるため
- 雑な比較機能は誤誘導しやすく、まずは測定条件を揃える運用を文書化する方が実務的なため

### 対象外

- UI 遷移時間の自動検出
- ボタン release から描画完了までの厳密な算出
- QML 外処理の断定
- 自動で計測条件の良し悪しを保証する機能

理由:

- 現在のトレース情報だけでは厳密性や断定性を確保しにくいため
- 実装しても誤検出や誤誘導のリスクが高いため

### 今回の対象外

- UI 遷移時間の自動検出
- ボタン release から描画完了までの厳密な算出
- QML 外処理の断定
- 自動で計測条件の良し悪しを保証する機能

理由:

- UI 遷移時間の自動検出
  - 入力イベントと、その後に続く一連の描画の対応付けが難しいため
  - アニメーションや段階的描画があると、完了点をトレースだけで一意に決めにくいため
- ボタン release から描画完了までの厳密な算出
  - UI 上の操作完了と profiler event の関係が常に 1 対 1 ではないため
  - 同一操作に対して複数の描画や非同期処理が混ざる場合があるため
- QML 外処理の断定
  - 親 range 内の空き時間は観測できても、その原因をトレースだけでは特定できないため
  - JavaScript, C++, import, I/O など複数の候補があり、空き時間だけで断定すると誤誘導になるため
- 自動で計測条件の良し悪しを保証する機能
  - 対象操作だけを切り出せているか、常駐アニメーションを止めるべきかはアプリごとの運用条件に依存するため
  - ツール単独では、計測時の前提条件が妥当だったかを保証できないため

## CLI 仕様案

### 方針

既存の `summary` は軽量な全体把握用として維持し、詳細解析は新コマンドに分離する。

理由:

- 親子関係や `self time` を含む出力は情報量が大きい
- 既存利用者の出力互換への影響を抑えたい
- 単純な件数確認と深掘り分析を分離したい

### 新規コマンド候補

#### `ranges`

range ごとの実体を時系列順または開始位置順で出力する。

候補出力項目:

- `startTime`
- `duration`
- `selfTime`
- `childTime`
- `gapTime`
- `depth`
- `eventIndex`
- `type`
- `display`
- `file`
- `line`
- `parentEventIndex` または親ノード識別子

用途:

- samegame のような親子重複の確認
- どのノードが真に重いかの確認

#### `hotspots`

重い箇所を親子関係込みで集約して出す。

候補出力項目:

- `type`
- `file`
- `line`
- `calls`
- `inclusiveTotal`
- `selfTotal`
- `maxInclusive`
- `maxSelf`
- `minInclusive`
- `medianInclusive`
- `outlierHint`
- `burstHint`

用途:

- 現行 `summary` の代替ではなく、深掘り用の上位表示

#### 複数トレース比較

`compare` コマンドで `hotspots` の `groupKey` ベース差分を表示する。
比較は `hotspots` に限定し、`ranges` の親子関係差分は各トレースを個別に見て確認する。

## データモデル拡張案

### 追加候補構造

#### `RangeNode`

- `id`
- `eventIndex`
- `startTime`
- `duration`
- `endTime`
- `parentId`
- `childIds`
- `depth`
- `inclusiveTime`
- `selfTime`
- `childCoveredTime`
- `gapTime`

### 算出ルール

- `inclusiveTime = duration`
- `childCoveredTime` は直下子 range の時間被覆長
- `selfTime = inclusiveTime - childCoveredTime`
- `gapTime` は親内部にある未説明時間

補足:

- 子 range が重ならない前提なら単純和でよい
- 重なりうるなら時間区間としてマージして被覆長を取る必要がある
- 同一開始時刻や同一終了時刻の並び順は明文化が必要

## 分析要件

### A. 親子関係復元

要件:

- range 開始時刻と終了時刻から入れ子構造を復元する
- 親不在の range を root として扱う
- 復元不能な異常並びは壊れたデータとして無視せず、可能な範囲で扱う

期待効果:

- 親子重複による誤解を減らす
- `Creating` / `Binding` の真のボトルネックを特定しやすくする

### B. self time

要件:

- 全 range に対して `selfTime` を算出する
- 集約時には `selfTotal`, `maxSelf` を出せるようにする

期待効果:

- 同じ処理を親子で重複評価しにくくなる
- 着目すべき leaf に近いノードが見える

### C. gap time

要件:

- 親 range に対して `gapTime` を算出する
- `gapTime` が大きい場合は注意表示できるようにする

表示方針:

- `QML外処理の可能性` と表現する
- JavaScript / C++ を断定しない

### D. 分布と外れ値

要件:

- 集約ごとに `count`, `min`, `max` を出す
- 少なくとも平均だけに依存しない
- 外れ値候補を簡易判定できるようにする

判定候補:

- `max` が `median` に対して十分大きい
- `count = 2` かつ `min/max` の差が極端

### E. バースト検出

要件:

- 同種イベントが短時間に集中した箇所を検出候補として出せる
- `ListView` / `Repeater` を断定しない
- `Creating` 群の件数と時刻集中を主要材料にする

## レポート方針

### 既存 `summary`

維持する。
ただし、将来的に次の注意書きを追加する余地がある。

- `totalDuration` は親子重複を含む
- `Creating` / `Binding` の解釈には `self time` が必要

### 新規詳細出力

詳細分析は `ranges` と `hotspots` に寄せる。

### 推定表示

次は断定せず、注意または候補として表示する。

- `Compiling` が大きい
- `import` 起因の隠れコストの可能性
- 画像やフォント影響の可能性
- QML 外処理の可能性

## 非機能要件

- 既存コマンドの出力互換をなるべく維持する
- 巨大トレースでも後から最適化しやすいデータ構造にする
- 単一トレース解析は deterministic であること
- 推定表示は根拠のある条件にのみ付ける

## 実装段階案

### Phase 1

- `RangeNode` 構築
- 親子関係復元
- `selfTime` / `gapTime` 算出
- `ranges` コマンド追加
- 基本テスト追加

### Phase 2

- 親子重複を避けるための着目ノード表示
- `summary` への注意表示追加
- `gapTime` の注意表示ルール追加

### Phase 3

- `hotspots` コマンド追加
- `count`, `min`, `max`, `median` などの集約
- 外れ値ヒント
- バーストヒント

### Phase 4

- 補助的な推定表示
- 比較運用ガイドの整備

## 未決事項

- 親子関係復元の並び順ルールをどう定義するか
- 子 range の重なりを一般ケースとして扱うか
- 外れ値判定の閾値を固定にするか
- バースト判定を時間窓ベースにするか
- 既存 `summary` に最小限の注意表示を入れるか

## 結論

`advice.txt` をすべてそのまま機能化するのではなく、次の三層で扱うのが妥当である。

1. 直近で実装する分析機能
2. 推定や注意表示として扱う知見
3. 運用ガイドに留める計測ノウハウ

直近の中心課題は、親子関係の復元と `self time` 導入である。
これがない限り、`Creating` / `Binding` の重さ評価は誤誘導を含みやすい。
