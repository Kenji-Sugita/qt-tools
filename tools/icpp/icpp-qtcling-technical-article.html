icpp + qtcling の構成

icpp と qtcling は、SRA が Qt/C++ の開発や調査を効率化するために開発した対話型ツールです。 qtcling は C++ インタープリターである Cling から Qt を使うための環境であり、 icpp は qtcling を扱いやすくする REPL ラッパーです。 REPL は Read-Eval-Print Loop の略で、入力したコードをその場で評価し、結果を表示し、次の入力へ戻る対話型の実行環境です。 Qt の型や QWidget をその場で試しながら、 編集、再実行、生成物の更新、オブジェクトの確認を行えるようにしています。 これにより、Qt と C++ の挙動を小さく確かめながら学べるため、習得の促進にも役立ちます。

Qt/C++ の開発では、短い確認でもソースを編集し、ビルドし、実行し直す流れになりがちです。 icpp + qtcling は、その確認作業を REPL 上で小さく回せるようにすることを目的としています。

icpp + qtcling は、デモ用に作ったツールではありません。 製作者自身が Qt/C++ のコードを確認し、QWidget の挙動を調べ、Designer UI やリソースを試すために日常的に使っている作業道具です。 小さく試してから本体プロジェクトへ戻す、という流れを短くするために機能を整えてきました。

この記事では、qtcling が Qt/C++ を対話的に動かす基盤として何を担い、 icpp がその上にどのような作業支援を追加しているのかを整理します。

なぜ Qt/C++ に対話環境が必要なのか

C++ / Qt の開発では、短い API の確認や小さな GUI 部品の試作でも、編集、ビルド、実行の往復になりがちです。 特に Qt では QObject、シグナル / スロット、プロパティー、リソース、翻訳、Designer UI など、 実際に動かして確認したい対象が多くあります。

確認作業のループを小さくする

対話環境があると、調べたいことを本体プロジェクトへ入れる前に、小さな単位で確認できます。 これは、Qt と C++ の習得、API 調査、生成されたコードの確認、GUI 部品の試作で効果があります。

qtcling とは何か

qtcling は、Cling の C++ REPL から Qt を対話的に使うための環境です。 QtCore、QtGui、QtWidgets を読み込み、REPL で Qt オブジェクトやウィジェットを作成して動かせます。

重要なのは、Qt GUI を表示した後も REPL 入力待ち中に Qt イベントを処理できることです。 これにより、画面上のウィジェットを操作しながら、REPL 側で状態を確認する流れを作れます。 必要に応じて setWindowTitle() や setText() などのメソッドを呼び出し、 表示中のウィジェットをその場で変更することもできます。

QWidget を表示したまま REPL 入力を続ける

REPL から表示した QWidget

Linux / WSL では、REPL 入力待ち中に Qt イベントを処理するために libedit の行編集対応が重要です。 Ubuntu / WSL では、qtcling をビルドする前に libedit-dev を入れておくと、 ボタンクリックなどの GUI イベントを REPL 入力待ち中にも処理しやすくなります。

icpp とは何か

icpp は、C++ を自分で解釈するツールではありません。 cling または qtcling を子プロセスとして起動し、その上に編集、再実行、複数ファイル管理、生成物更新、 表示補助などの REPL 作業支援を追加するラッパーです。

既定では qtcling を使うため、QString、QVariant、QWidget などの Qt 型をすぐ試せます。 標準で読み込まれていない Qt モジュールも、必要に応じて追加して試せます。 たとえばネットワーク処理を確認したい場合は、Qt Network のヘッダーやライブラリーを追加して使います。 Qt を使わない C++ の確認では、cling を明示して使うこともできます。

利用前提

この記事で扱う対象は、icpp 1.0.1 と qtcling 1.0.1 です。 icpp は macOS または Linux で使うことを前提にしています。 Windows では Windows ネイティブ版ではなく、Windows 11 の WSL2 / WSLg 上の Linux 環境で使う方針です。 Windows ネイティブ版は今後の実装予定です。 Qt は Qt 6 を前提にし、CMake 3.16 以降、動作する cling または qtcling が必要です。

qtcling を使う場合は、icpp、qtcling、Qt の開発ツール、.inspect で使う補助ライブラリーなどを、 同じ Qt 6.x.y の環境で揃える運用を推奨します。 Qt 6 同士でもマイナーバージョンが違う Qt ライブラリーや生成物を同じ qtcling プロセスに混ぜると、 不安定になる可能性があります。

入力編集とコマンド履歴には GNU Readline または libedit を使います。 Ubuntu 24.04 や WSL2 では、ビルド前に libedit-dev を入れておくと、 矢印キーによる編集や履歴を使えるようになります。 見つからない場合は標準入力にフォールバックします。

.inspect を使う場合は、PropertyEditor の共有ライブラリーと、 ObjectPicker / ObjectTree / PropertyEditor 関連ヘッダーを icpp 実行ファイルから見える位置に置きます。 Linux / WSL2 では property_editor.so、macOS では property_editor.dylib を使います。 必要に応じて ICPP_PROPERTY_EDITOR_LIB と ICPP_PROPERTY_EDITOR_INCLUDE で明示できます。

icpp + qtcling でできること

icpp + qtcling は、Qt/C++ の小さな確認を REPL 上で進めるための作業環境です。 代表的な使い方は次のとおりです。

典型的には、数行の QWidget をファイルに書き、REPL から呼び出す入口として go() を用意し、 go() で作成して show() します。 表示した後も REPL に戻れるため、ウィンドウを見ながら状態を確認できます。

具体的な go() の定義例と実行手順は、後の「QWidget を表示したまま REPL を続ける」で示します。 Qt 生成物が必要な場合は、.gen で更新してから再評価します。

目的 主なコマンド
値を表示する .p
型を確認する .ptype
ファイルを編集して再実行する .e, .add, .r
Qt 生成物を更新する .gen, .generated, .qt
表示中のウィジェットを調べる .widgets, .inspect
環境を確認する .doctor

最小の使い方: Qt 型、値、型名をその場で確認する

短い確認では、Qt 型の値を作り、.p で表示し、.ptype で型を確認します。 たとえば QStringList や QVariant の内容をすぐに確認できます。 

icpp[qtcling]> using namespace Qt::Literals::StringLiterals;
icpp[qtcling]> QLatin1StringView key = "Content-Type"_L1;
icpp[qtcling]> .ptype key
QLatin1StringView (meta: QLatin1String)
icpp[qtcling]> QUtf8StringView view = u8"example";
icpp[qtcling]> .ptype view
QUtf8StringView

型の表示は、Qt の内部実体名ではなく、普段コードで使う公開名を優先します。 そのため、REPL で確認した結果を実際のソースコードへ戻しやすくなります。

QWidget を表示したまま REPL を続ける

icpp + qtcling では、QWidget を作成して表示した後も REPL で入力を続けられます。 表示中のウィジェットに対してメソッドを呼んだり、状態を確認したりできます。

スクリーンショットでは、次のような小さな Widget クラスを用意しています。 go() は REPL から呼び出すための入口で、作成したウィジェットを返すだけにします。 

// widget.cpp
#include <QHBoxLayout>
#include <QLabel>
#include <QLineEdit>
#include <QPushButton>
#include <QVBoxLayout>
#include <QWidget>

class Widget : public QWidget {
    Q_OBJECT

public:
    explicit Widget(QWidget *parent = nullptr) : QWidget(parent) {
        titleLabel = new QLabel("Counter", this);
        titleLabel->setAlignment(Qt::AlignCenter);

        valueEdit = new QLineEdit(this);
        valueEdit->setAlignment(Qt::AlignCenter);
        valueEdit->setReadOnly(true);

        auto *downButton = new QPushButton("Down", this);
        auto *upButton = new QPushButton("Up", this);

        connect(downButton, &QPushButton::clicked, this, [this]() {
            --count;
            updateView();
        });
        connect(upButton, &QPushButton::clicked, this, [this]() {
            ++count;
            updateView();
        });

        auto *layout = new QVBoxLayout(this);
        layout->addWidget(titleLabel);
        layout->addWidget(valueEdit);

        auto *buttons = new QHBoxLayout;
        buttons->addWidget(downButton);
        buttons->addWidget(upButton);
        layout->addLayout(buttons);

        resize(360, 360);
        updateView();
    }

private:
    void updateView() {
        valueEdit->setText(QString::number(count));
        setWindowTitle(QString("Counter: %1").arg(count));
    }

    QLabel *titleLabel = nullptr;
    QLineEdit *valueEdit = nullptr;
    int count = 0;
};

Widget *go() {
    return new Widget;
}

Qt 生成物を扱う: .gen で必要なファイルを更新する

Qt の通常のコードは、C++ ソースだけでは完結しないことがあります。 Q_OBJECT を含むクラス、Designer UI、リソースを使うコードでは、Qt が作る生成物が必要です。 icpp では、利用者が個々の生成ツールを直接意識するのではなく、.gen で必要な生成物をまとめて更新します。

入力 生成物 主な用途
widget.h メタオブジェクト用の C++ ファイル シグナル / スロット、プロパティー、メタオブジェクト情報
form.ui UI 用の C++ ヘッダー Qt Designer で作成した UI の C++ ヘッダー
resources.qrc リソース用の C++ ファイル 画像、テキスト、翻訳ファイルなどのリソース

.gen と .generated で Qt 生成物を扱う

icpp の .gen は、必要な Qt 生成物を更新し、必要に応じてインタープリターを再起動して登録ファイルを評価し直します。 クラス定義の再定義に制約がある REPL では、生成後に作り直す運用が安定します。

.ui / .qrc / .ts を専用ツールで編集する

icpp は、Qt Designer、Qt Creator のリソースエディター、Qt Linguist を置き換えません。 専用ツールで編集し、保存後に icpp 側で生成物を更新する流れを支援します。

翻訳では、Qt 標準の lupdate / lrelease を明示的に実行します。 icpp はこれらの短縮 alias を用意せず、オプションを隠さない方針です。

.inspect で QWidget / QObject を調べる

.inspect は、表示中の最上位ウィジェットを選び、PropertyEditor、Object Tree、Object Picker を使って QObject / QWidget の状態を確認するための機能です。

GUI の不具合は、コードだけを読んでも分かりにくい場合があります。 実行中の objectName、プロパティー、親子関係を直接見られると、UI と C++ 側の参照のずれを確認しやすくなります。

Qt Creator と併用する

icpp は Qt Creator の代替 IDE ではありません。 Qt Creator はプロジェクト、CMake、Kit、補完、デバッグ、テストを担当し、 icpp は小さな Qt/C++ 実験、確認、生成、検査を担当します。

Qt Creator と icpp を横に置いて使う

作業 主に使う道具
本体プロジェクトの編集、ビルド、デバッグ、テスト Qt Creator
小さな Qt/C++ API の確認 icpp + qtcling
.ui の編集 Qt Designer または Qt Creator
.qrc の編集 Qt Creator のリソースエディターまたはテキストエディタ
.ts の翻訳編集 Qt Linguist

使いどころと対象外

icpp + qtcling は、Qt/C++ の小さな実験、API 確認、QWidget 試作、生成されたコードの確認、学習に向いています。 一方で、本格的なビルドシステム、長期運用アプリの実行基盤、Qt Creator のプロジェクトモデルの代替ではありません。

まとめ

qtcling は、Qt/C++ を REPL で動かすための基盤です。 icpp はその上に、編集、再実行、生成、検査の作業支援を追加します。

icpp + qtcling は、Qt Creator と競合するものではありません。 Qt Creator で本体開発を行い、icpp + qtcling で小さな確認を素早く回すことで、 Qt/C++ の調査、試作、学習を進めやすくします。
