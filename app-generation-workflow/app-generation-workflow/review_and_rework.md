# レビューと手戻りの判定手順

この手順は、要求から設計・運用判断までの各工程で、開始、確認、前工程への手戻り、再実行、停止を判断するために使う。
`three_key_documents_workflow.md` の工程を具体化する付属手順であり、同じディレクトリに置く。
AI は証拠と指摘を整理し、人は仕様の採用、業務判断、対象外、リスク受容を決める。
レビューだけを依頼された場合は判定と修正案を返し、修正作業の依頼を受けてから成果物を変更する。

## 1. 共通の判定方法

### 1.1 開始時に固定するもの

工程を始める前に、対象範囲、使う正本、確認対象の版、確認方法、期待結果を記録する。
版はコミットだけでなく、未コミット差分、対象ファイル、変更項目を特定できる記録でもよい。
仕様化前ノートの正本は `source_memo.md` または `five_source_memos/` のどちらか一方とする。
相対パスには基準ディレクトリを付け、参照画像も実在する資産と対応させる。
正本、対象範囲、期待結果が分からない場合は、その不足を解消する工程へ戻る。

各工程の確認は、次の順で行う。

1. 入力と開始条件を確認する。
2. AI が元資料と成果物を照合し、指摘ごとに根拠と影響を示す。
3. 人が採用・業務判断を要する指摘を決める。既に承認された内容の転記や実装の修正では、その根拠を記録する。
4. 修正が必要なら修正作業へ返し、変更後の版で再確認する。
5. 通過条件を満たした範囲と、次工程を止める未解決事項を記録する。

### 1.2 通過を止める指摘

この手順でいう「重大な不整合」は、次のいずれかに該当する工程を止める指摘である。
件数や文章量で重大性を決めない。

- 次工程で要求、業務ルール、対象外、成功・失敗時の結果を推測しなければならない。
- 正本同士、正本と成果物、期待結果と確認結果が食い違う。
- 仕様への反映漏れ、採用未確認の仮決め、対象外への追加がある。
- 当該工程に必要な確認の根拠、環境、実行結果がなく、受入条件を判定できない。
- データ保護、権限、外部契約、互換性など、今回の対象に関わる重要な判断が未決である。

単なる誤字など、意味、参照先、期待結果、後工程の判断に影響しないものは、理由と修正予定を残して保留できる。
影響を説明できない場合は工程を止める指摘として扱い、人へ確認する。
「既知差分」「残リスク」と名前を付けるだけでは、仕様違反や必須確認の未実施は解消しない。
範囲を縮めて進める場合は、人が対象範囲を決め、要求・ノート・関連仕様に反映してから、その範囲で判定し直す。

未決事項の既存の1行形式は維持し、その項目の記録に、影響範囲、止める工程、質問、再開に必要な回答を添える。
次工程に影響しない根拠と決定期限となる工程が分かる項目だけを保留できる。
`- なし` は採用判断と反映が完了した結果として記載し、未決事項を削除するだけで通過させない。

### 1.3 判定と状態

| 判定 | 条件と次の動作 |
| --- | --- |
| 通過 | 対象範囲の必須確認が完了し、工程を止める指摘がなく、必要な人の判断が記録されている。次工程へ進む |
| 修正待ち | 根拠と戻り先が特定でき、現在の依頼範囲内で修正できる。該当工程へ戻す |
| 人の判断待ち | 採否、範囲、優先順位、矛盾する要求の解消が必要。質問と選択肢を示して当該範囲を止める |
| 確認不能 | 入力、環境、権限、結果が不足する。未実施の確認と再開条件を示す |
| 中止 | 人の中止指示、または事前に決めた作業範囲・時間等の上限に達した。状態と残作業を保存する |

通過は工程・範囲・版ごとの判定であり、アプリ全体の完成や配布承認とは区別する。
環境が不足していても読める資料の照合は行えるが、部分レビューを実行確認済みとは記録しない。
対象外の確認は、その理由と範囲の採用判断を記録する。未実施を対象外へ読み替えない。

## 2. 戻り先を選ぶ

問題の現れたファイルと、修正を始める正本を分けて判断する。
まず要求と採用判断を確認し、ノート、三点セット、実装条件、プロンプト、コード、テスト、契約・設計のどこで初めて食い違ったかを探す。

| 問題の種類 | 確認して戻す場所 | 後続への反映 |
| --- | --- | --- |
| 要求そのものの不足・矛盾 | 要求と人の採用判断 | 要求を決め、ノートから後続へ反映する |
| 業務上の意味、表示、操作、対象外の変更・新たな決定 | 仕様化前ノート | 三点セット、プロンプト、コード、テスト、契約・設計へ順に反映する |
| ノートは正しいが三点セットへの転記が誤る | ノートの該当項目を確認して三点セット生成・レビューへ戻る | ノートの意味は変えず、三文書間と後続の対応を再確認する |
| ビルド互換性・実装方式が未決または指示が古い | 人が決めた実装方式、共通実装制約、実装プロンプト | 制約・プロンプトを整合させてからコードとビルドを再確認する |
| 上流は正しいがコードが従っていない | 該当仕様と有効な実装プロンプトを確認し、コード生成・修正へ戻る | 正しい仕様は書き換えず、対象箇所と確認項目を指示して修正する |
| 仕様と違うテスト期待値 | 三点セットのルールと代表例を確認してテスト作成へ戻る | 仕様から期待値を導き直す。仕様が曖昧なら先にノートへ戻る |
| ビルド・実行環境の不足 | ビルド手順、依存関係、実際のエラー | 環境が原因と確認できた範囲を復旧する。原因不明のままコードや仕様を変えない |
| 契約・設計への記載漏れ | 元仕様・コード・資産・確認結果を照合して文書生成工程へ戻る | 上流が正しければ当該文書のみ修正し、関連記述を再レビューする |

既存アプリの再生成では、承認済みの契約を維持条件の根拠として参照する。
新しく維持すべき構造が見つかった場合は、人が採用した条件をG04・G05へ反映してから再生成する。
契約の改訂草案は先に検討できるが、変更後の実装との対応を確定するのはG10再通過後とする。

上流に変更が不要な場合も、確認した正本の箇所と、変更不要とした理由を記録する。
コード修正は、有効な実装プロンプトに従う修正作業として行う。指示が不足していれば先にプロンプトを直す。
要求の原文と後から採用されたノートが異なる場合は、採用記録を追跡する。原文を無理に書き換えず、いつ何を変更したかを関連付けてもよい。
採用記録が見つからない場合は人へ確認し、後発文書というだけで正しいと決めない。

## 3. 再実行と停止

### 3.1 再実行を始める条件

再実行前に、解消対象の指摘、修正した入力・成果物または環境、期待する変化、再確認範囲を記録する。
同じ入力と方法のまま、理由なく生成・レビュー・テストを繰り返さない。
一時的な外部障害を再試行する場合は、復旧根拠または一時障害の根拠と、回数・時間の上限を決める。

上流を変更したら、依存する後工程の通過判定を「再確認待ち」に戻す。
古い結果は履歴として保持し、新しい版の合格証拠にはしない。

| 変更したもの | 少なくとも再確認する範囲 |
| --- | --- |
| 要求・ノート | 該当仕様、三文書間の対応、プロンプト、影響する実装・期待値・テスト、契約・設計 |
| 三点セット・実装制約・プロンプト | ノートとの整合、影響する実装、ビルド、テスト、実装結果レビュー、契約・設計 |
| コード・ビルド設定 | ビルド、関係する自動テスト・手動確認、実装結果レビュー、影響する契約・設計 |
| テスト期待値・手動確認項目 | 元仕様との照合、修正した確認の実行、実装結果レビューの判定 |
| 契約・設計の記述のみ | 元資料との照合、関連文書と文書内の整合、設計書レビュー |
| 実行環境のみ | 失敗・未実施だった確認と、その結果を受ける実装結果レビュー・運用判定 |

範囲を限定する場合は、変更項目と依存先を列挙する。
影響がないため再実行しない項目は、保持する結果の版と理由を記録する。
影響範囲を判断できなければ、当該成果物に依存する全範囲を再確認対象にする。

### 3.2 反復を止める条件

- 修正後も同じ原因の指摘が再発し、次に変える根拠を説明できない場合は、再生成を止めて人へ修正方針を返す。
- 新しい要求の採用、対象外の変更、重要な業務判断が必要になったら、当該範囲を人の判断待ちにする。
- 必須入力・確認環境がない、または指定上限へ達した場合は、確認不能または中止とする。
- 人から中止の指示があれば止め、変更済み成果物、未解決事項、再開条件を保存する。

いずれも証拠のない完了扱いにしない。依存しない別範囲は、独立している根拠を示せる場合に進められる。
繰り返す問題は、今回の修正と分けて、原因、手順・テンプレートの不足、次回改善案を記録する。
対象アプリの修正中にコピー済みワークフローを変更せず、ワークフロー保守の作業へ返す。

## 4. 工程別の条件

各工程は1節の判定、2節の戻り先、3節の再実行・停止条件を共通して使う。
「停止」は当該工程から後続への通過を止める意味であり、原因調査まで禁止する意味ではない。

### G01 要求確認と対象範囲の確定

- 開始条件: 要求原文、目的、対象作業が特定できる。原文がない既存コードでは、R01で整理した観測資料と人の採用判断を要求入力とする。
- 確認方法: ヒアリング9項目、主な状態・操作、例外・境界値、代表例、対象外、未決事項を要求と照合する。AIの推薦案と採用済み要求を分ける。
- 通過条件: ノートと三点セットに必要な判断がある。後工程まで保留できる項目は、影響しない理由と止める工程を記録している。
- 戻す条件と戻り先: 目的・操作・業務ルールが矛盾または不足するなら、要求と人の採用判断へ戻す。
- 再実行条件: 人の回答または採用内容が要求・判断記録に反映され、依存する項目を再照合できる。
- 停止条件: 要求の採否が未確認、または次工程で推測が必要なら人の判断待ちとする。

### G02 仕様化前ノートの作成とレビュー

- 開始条件: G01を通過し、対象アプリ用ディレクトリと単一・分割の正本を決めている。
- 確認方法: 要求の各項目からノートへの対応、対象外、未決事項、代表例、期待結果、参照資産を照合する。採用未確認の内容が断定されていないかを見る。
- 通過条件: 要求と採用判断を追跡でき、三点セット生成を止める未決事項・矛盾がなく、人が内容を確認している。
- 戻す条件と戻り先: 要求不足はG01、反映漏れは正本ノートへ戻す。原文との差は採用記録で確認する。
- 再実行条件: 変更箇所と決定を反映し、対応関係、未決事項、関連する代表例を再照合する。
- 停止条件: 正本を選べない、または重要なルール・参照資産の採用を判断できない場合は止める。

### G03 三点セットの生成とレビュー

- 開始条件: G02を通過した正本ノートがあり、レビュー段階を選んでいる。
- 確認方法: UCの目的・成功条件、UIの入力・表示・操作、業務仕様の検証・計算・保存を、ノートと三文書相互で照合する。正常・異常・境界値の期待結果を導く。
- 通過条件: 対象外と保留項目を含め三文書が整合し、実装方式を決められ、人が仕様として確認している。
- 戻す条件と戻り先: 判断不足・変更はG02、転記漏れはノートの根拠を確認してG03へ戻す。
- 再実行条件: 該当箇所と関連する三文書・期待結果を修正し、文書間レビューをやり直せる。
- 停止条件: 同じ入力への期待結果が異なる、または未決事項が実装を左右する場合は止める。

### G04 実装方式と共通実装制約

- 開始条件: G03を通過し、利用環境と既存プロジェクトの制約を参照できる。
- 確認方法: 言語、フレームワーク、ビルド・テスト方式、依存関係、保存方式、変更禁止範囲を確認する。業務上の保存要否と技術的な保存手段を区別する。
- 通過条件: 人が必要な実装方式を決め、共通制約の有無と参照先が分かる。
- 戻す条件と戻り先: 技術選択の未決はG04、利用者の挙動・保存要否を変える判断はG02へ戻す。
- 再実行条件: 採用した方式・制約と対応する検証方法がそろう。
- 停止条件: 互換性、依存関係、変更可能範囲を決められず、プロンプトを具体化できない場合は止める。

### G05 実装プロンプトの作成とレビュー

- 開始条件: G03・G04を通過し、参照する正本、対象ディレクトリ、実装範囲が決まっている。
- 確認方法: 参照先の実在、版、ノート・三点セット・制約の対応、必須欄、ビルド方法、テスト可能性、対象外、未決事項を照合する。
- 通過条件: テンプレートの空欄・古い参照がなく、今回の実装を指示でき、人が方式と範囲を確認している。
- 戻す条件と戻り先: 仕様判断はG02、三点セットの反映漏れはG03、技術選択はG04、指示の転記漏れだけならG05へ戻す。
- 再実行条件: 参照と指示を更新し、影響する仕様・制約との対応を再確認できる。
- 停止条件: 必須ファイル不在、対象不明、未記入、実装に影響する未決事項があれば止める。

### G06 コード生成と構成確認

- 開始条件: G05を通過し、対象ディレクトリ、変更許可範囲、保護するファイルを特定できる。
- 確認方法: 生成差分、必要ファイル、UIと業務処理の境界、仕様外追加、既存API・保存形式・依存関係への影響を確認する。
- 通過条件: 指示した範囲の生成が完了し、構成と差分が説明でき、G07で検証できる。
- 戻す条件と戻り先: 指示不足はG05、仕様不足はG02、明確な実装漏れは有効なプロンプトの下でG06へ戻す。
- 再実行条件: 修正対象と維持する仕様・ファイルを指示でき、前回から変える根拠がある。
- 停止条件: 保護対象の変更、未承認の機能追加、生成結果の意味を判定できない差分があれば止める。

### G07 ビルド

- 開始条件: G06のコードとビルド手順、ツールチェーン、必要な依存関係がそろっている。
- 確認方法: 対象ディレクトリで構成・ビルドを実行し、コマンド、環境、終了結果、エラー箇所を記録する。
- 通過条件: 対象版・対象環境で構成とビルドが成功し、成果物を特定できる。
- 戻す条件と戻り先: エラーの根拠から環境不足は環境・手順、制約漏れはG04・G05、コード不良はG06へ戻す。
- 再実行条件: 環境復旧、指示またはコード修正後、必要な再構成を含む同じ受入ビルドを実行できる。
- 停止条件: 必須ツール不在、依存関係取得不能、原因未特定の場合は確認不能とする。ビルド失敗を直すために機能仕様を緩めない。

### G08 自動テストと手動確認項目の作成

- 開始条件: G07を通過し、レビュー済み仕様・プロンプト・コードを参照できる。
- 確認方法: 仕様IDまたは項目から、入力、前状態、操作、期待結果、正常・異常・境界値を導く。期待値は仕様の式・ルールから計算し、コードの出力と独立に確認する。
- 通過条件: 必要な自動・手動確認の対象、手順、期待結果がそろい、人が期待値の妥当性を確認している。テストコード・ビルド設定を追加変更したらG07へ戻り、再構成とビルド後にG09へ進む。
- 戻す条件と戻り先: 期待結果の未決はG02・G03、テストしにくい構造はG05・G06、テストへの転記ミスはG08へ戻す。
- 再実行条件: 根拠ルールまたはテスト項目を修正し、期待値と境界値を再照合できる。
- 停止条件: コードからしか期待値を説明できない、または必要な確認を列挙できない場合は止める。

### G09 自動テストと手動確認の実行

- 開始条件: G08を通過した項目と、テスト追加変更後にG07を通過した成果物・検出テスト一覧があり、実行環境・参照資産を利用できる。
- 確認方法: テストを実行し、実行数、対象、期待結果との差を記録する。手動確認は操作・入力と表示・状態の結果を項目ごとに残す。
- 通過条件: 対象範囲の必要な自動テスト・手動確認が成功している。対象外は理由と人の判断が記録されている。
- 戻す条件と戻り先: テスト定義の誤りはG08、仕様に反する実装はG06、意図した挙動の未決はG02、環境不足は確認環境へ戻す。
- 再実行条件: 修正後にG07のビルドを確認し、失敗項目と影響する回帰項目を実行できる。
- 停止条件: 失敗、未実施、テスト未検出、UIを確認できない場合は、その範囲の通過を止める。自動テスト成功をUI確認や配布承認へ流用しない。

### G10 実装結果レビューと仕様への反映確認

- 開始条件: G06〜G09の結果がある。失敗・確認不能があっても原因分類のための部分レビューは開始できる。
- 確認方法: 正本からコード・テストまで追跡し、仕様外追加、仮決め、参照資産、未確認項目を列挙する。各指摘に2節の戻り先を付ける。
- 通過条件: G07〜G09を通過し、重大な不整合、仕様への反映漏れ、未解決の仮決めがないことを人が確認している。
- 戻す条件と戻り先: 原因を持つ最上流の工程へ戻す。採用された変更はノートから関連成果物へ反映する。
- 再実行条件: 修正とG07〜G09の必要な再確認が終わり、指摘と反映先の対応を再レビューできる。
- 停止条件: 部分レビューのみ、必須確認未完了、採用判断未了ならG11へ通過させない。

### G11 実装設計契約の作成と確認

- 開始条件: 新規作成・確定にはG10を通過した同じ版の仕様・コード・確認結果がある。既存契約の維持条件の検討・改訂草案はG10未通過でも開始できるが、確定扱いにはしない。
- 確認方法: 仕様項目と実装箇所、公開API、構成、テスト、参照画像、手動確認、残リスクの対応を確認する。
- 通過条件: 実装との対応が追跡でき、未確認項目や既知差分を確定仕様と混同せず、人が確認している。
- 戻す条件と戻り先: 契約だけの記載漏れはG11、上流との食い違いはG10から原因工程へ戻す。
- 再実行条件: 元資料を確認して記載を修正したか、上流の再通過後に契約を更新できる。
- 停止条件: 仕様違反を現状コードの契約として固定する、または重大な不整合を見つけた場合は完成扱いにしない。

### G12 アプリ設計書の作成

- 開始条件: G11を通過し、同じ版の三点セット、契約、コードを参照できる。
- 確認方法: 構成、責務、主要処理、エラー、資産、テスト、ビルド・運用を元資料へ対応付ける。
- 通過条件: 参照仕様とコードを追跡できる草案があり、未確認・既知差分を区別してG13で照合できる。
- 戻す条件と戻り先: 記載漏れはG12、契約不足はG11、仕様・実装の不整合はG10へ戻す。
- 再実行条件: 修正済み元資料から該当設計を更新できる。
- 停止条件: 仕様・契約・コードが矛盾する場合は断定して取り込まず、指摘として返す。

### G13 設計書レビューと最終整合確認

- 開始条件: G12の草案と、G11までで使用した版・確認結果がある。
- 確認方法: 仕様、契約、実装、設計書の対応と文書内の矛盾を確認する。資産パス、既知差分、未テスト項目の欠落を確認する。
- 通過条件: 重大な不整合がなく、人が設計として確認している。
- 戻す条件と戻り先: 文書だけの誤りはG11・G12、実装不一致はG10、仕様判断の変更はG02へ戻す。
- 再実行条件: 文書修正後は関連記述を再レビューする。コードや仕様を変えた場合は該当工程からG10以降も再通過する。
- 停止条件: 仕様不一致、未承認の追加、古い結果での合格記載があれば確定しない。

### G14 運用判断と引き継ぎ

- 開始条件: G13までの対象範囲が通過し、READMEと必要な運用情報を確認できる。
- 確認方法: 対象環境、ビルド・テスト・起動手順、確認済み範囲、配布条件、残リスクと許可する運用段階を照合する。
- 通過条件: 人が当該運用段階を決め、READMEと再開メモへ根拠と未完了を保存している。
- 戻す条件と戻り先: 手順の記載漏れはREADME、検証不足はG07〜G09、仕様・設計の矛盾は原因工程へ戻す。
- 再実行条件: 不足条件を確定・検証し、運用段階を判定し直せる。
- 停止条件: 配布形式、対象環境、依存関係・ライセンス、起動手順、必須手動確認が未確定なら利用者配布を止める。作業終了時の途中状態保存は通過前でも行う。

## 5. 分岐する工程

### R01 既存コードの逆生成

- 開始条件: 対象コード・版、分かる範囲の実行結果、既存資料がある。
- 確認方法: 観測したUC・UI・業務処理と、推測・バグ候補を分ける。AI確認後に人が観測結果を確認し、逆生成レビュー用ノートでもAI確認後に人が採用判断を行う。
- 通過条件: 採用する挙動、修正する挙動、対象外、未決事項が分かれている。要求原文がない場合も、この観測資料と採用判断をG01の要求入力として範囲を確認し、G02・G03で正式仕様を作成・レビューできる。
- 戻す条件と戻り先: 読み取り漏れは観測・逆生成へ、何を正しい仕様とするかの判断は人へ戻す。
- 再実行条件: 追加の実行証拠または採用判断を記録し、境界値と代表例を再確認できる。
- 停止条件: 現状と採用仕様を区別できない、または未観測の挙動を断定する必要があれば止める。

### R02 ノートの分割と正本切り替え

- 開始条件: 分割対象、現在の正本、人の分割判断を特定できる。最初から分割する場合はG01の要求を使う。
- 確認方法: 移行前後の各項目、用語、共通ルール、代表例、対象外、未決事項を対応付け、参照先の切り替えを確認する。
- 通過条件: 移行漏れ・意味の変化がなく、`five_source_memos/` を唯一の正本としてG02・G03を確認できる。
- 戻す条件と戻り先: 移行漏れは分割作業、意味の変更を要するものはG02の採用判断へ戻す。
- 再実行条件: 対応表と参照先を修正し、関連する三点セット・プロンプトも再確認できる。
- 停止条件: 新旧のどちらが正本か判断できない、または未決事項が失われた場合は切り替えない。

## 6. 判定を残す

対象アプリの既存レビュー報告や作業記録に、工程、対象版、範囲、証拠、指摘、判定、戻り先、再開条件を残す。
要求確認だけのために専用ファイルを必須にはしない。
形式が必要なら `templates/review_record.md` を使う。
過去の指摘と現在の指摘を混ぜず、修正前の判定、修正した内容、再確認後の判定を追跡できるようにする。

事例への机上適用結果は、配布物の `docs/workflow_review_case_studies.md` を参照する。
