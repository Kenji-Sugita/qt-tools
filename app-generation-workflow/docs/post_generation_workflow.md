# コード生成後の作業手順

この文書は、対象アプリのコード生成後に、仕様、設計、実装、テスト、運用手順の整合性を確認し、運用判断へ進めるための汎用手順を定義する。

## 1. 前提

コード生成後の作業は、対象アプリ用ディレクトリに次の文書とコードが存在する状態から開始する。

- `source_memo.md` または `five_source_memos/`
- `specs/01_usecase_spec.md`
- `specs/02_ui_spec.md`
- `specs/03_business_spec.md`
- `prompts/implementation_prompt.md`
- `include/`
- `src/`

`implementation_design_contract.md` と `app_design.md` は、実装結果レビューで重大な不整合がないことを確認した後に作成する。

## 2. 作業の目的

- 生成コードが仕様と一致していることを確認する。
- コード生成後に、仕様に基づく自動テストと手動確認項目を作成する。
- 自動テストと手動確認で運用可能性を判断する。
- 必要な場合は、仕様化前ノート、三点セット、実装プロンプト、コードの順に戻して整合させる。
- 実装結果レビュー後に、実装設計契約とアプリ設計書を作成する。
- 運用手順を `README.md` に残す。
- 次回再開に必要なコンテキストを対象プロジェクトの再開メモに保存する。

## 3. 全体手順

1. 生成コードの構成を確認する。
2. 仕様、実装プロンプト、コードを照合する。
3. ビルドする。
4. 自動テストと手動確認項目を作成する。
5. 自動テストを実行する。
6. UIまたは主要操作を手動確認する。
7. 実装結果をレビューする。
8. 重大な不整合があれば、仕様へ戻して修正する。
9. 未解決の重大な不整合がないことを確認する。
10. `implementation_design_contract.md` を作成する。
11. `app_design.md` を作成する。
12. `app_design.md` をレビューする。
13. 運用判断を文書へ反映する。
14. `README.md` を更新する。
15. 対象プロジェクトの再開メモにコンテキストを保存する。
16. コミット前確認を行う。
17. 必要に応じてコミットする。

## 4. 生成コードの構成確認

次を確認する。

- リポジトリまたはプロジェクトの既存構成に沿っていること。
- 既存のコーディング規約、設計方針、ファイル分割方針に反していないこと。
- UI、アプリケーション制御、ビジネスロジック、データ処理の責務が混ざりすぎていないこと。
- テスト対象にすべきロジックが、手動確認だけに依存していないこと。
- ビルドと起動に必要なファイルがそろっていること。
- テストを追加する場所、テストフレームワーク、実行方法を判断できる構成になっていること。

## 5. 仕様と実装の照合

次の順で確認する。

1. `source_memo.md` または `five_source_memos/` の仕様判断が三点セットに反映されていること。
2. 三点セットの内容が `prompts/implementation_prompt.md` に反映されていること。
3. `prompts/implementation_prompt.md` の指示が `include/`、`src/` に反映されていること。
4. 参照画像、外部参照資産、文言、手動確認対象など、コードだけでは復元しにくい情報が失われていないこと。
5. 実装時の仮決め、既知差分、未テスト項目が放置されていないこと。

不整合が見つかった場合は、コードだけを直接修正しない。
仕様変更であれば仕様化前ノートから、仕様書の不足であれば三点セットから、実装漏れであれば実装プロンプトとコードの対応から修正する。

## 6. ビルド

対象アプリ用ディレクトリで、プロジェクトのビルド手順を実行する。

例:

```sh
cmake -S . -B build
cmake --build build
```

プロジェクト固有の環境変数、ライセンス回避設定、ツールチェーン指定、依存関係の取得手順がある場合は、`README.md` または対象アプリの運用手順に明記する。

## 7. テスト作成と自動テスト

コード生成後に、三点セット、実装プロンプト、実装コードを参照して、自動テストと手動確認項目を作成する。
コードだけから期待値を作らない。
実装コードが仕様と違う場合は、テストに合わせて固定せず、不整合として列挙する。

自動テストでは、主に次を確認する。

- 入力検証
- データ正規化
- 主要な業務ルール
- 境界値
- 例外またはエラーケース
- 状態遷移
- 回帰しやすい計算、変換、判定

テストを作成したら、対象アプリのテスト手順を実行する。

例:

```sh
ctest --test-dir build --output-on-failure
```

## 8. 手動確認

自動テストでは、見た目、操作感、外部連携、端末差、表示崩れを完全には保証しない。
コード生成後に作成した手動確認項目に従って、対象アプリの性質に応じた確認を行う。
手動確認では、次を確認する。

- アプリが起動すること。
- 初期表示または初期状態が仕様通りであること。
- 主要操作が仕様通りに動作すること。
- 正常系の代表例が仕様通りに完了すること。
- 入力エラー、通信エラー、未選択、空データなどの異常系が仕様通りに表示されること。
- 直前の結果や状態を保持すべき場面で、意図せず破棄されないこと。
- 参照画像やUI仕様がある場合、画面構成、文言、主要な配置が逸脱していないこと。
- 外部参照資産がある場合、読み込み、表示、欠落時の扱いが確認されていること。

## 9. 実装結果レビュー

ビルド、テスト作成、自動テスト、手動確認の後、`implementation_design_contract.md` や `app_design.md` を作る前に、実装結果をレビューする。

確認する内容:

- 仕様化前ノート、三点セット、実装プロンプト、コードの間に矛盾がないこと。
- 実装時の判断が、仕様へ戻すべき内容を勝手に確定仕様として扱っていないこと。
- 参照画像、外部参照資産、手動確認対象が失われていないこと。
- 未解決の仮決め、既知差分、未テスト項目が明示されていること。

重大な不整合、仕様への反映漏れ、未解決の仮決めがある場合は、`implementation_design_contract.md` や `app_design.md` を作らない。

## 10. 仕様へ戻す

不整合は種類ごとに反映先を分ける。

| 不整合 | 反映先 |
| --- | --- |
| 仕様判断が不足している | `source_memo.md` または `five_source_memos/` |
| ユースケース、状態遷移が違う | `specs/01_usecase_spec.md` |
| 画面、表示、操作、文言が違う | `specs/02_ui_spec.md` |
| 業務ルール、計算、検証、正規化が違う | `specs/03_business_spec.md` |
| 実装指示が古い | `prompts/implementation_prompt.md` |
| コードが仕様または実装指示を満たしていない | `include/`, `src/`, `tests/` など |
| 運用手順が古い | `README.md` |
| 再開メモが古い | `NEXT.md` |

修正後は、ビルド、自動テスト、必要な手動確認、実装結果レビューを再実行する。
未解決の重大な不整合がある間は、後続の設計文書を完成扱いにしない。

## 11. 実装設計契約を作成する

実装結果レビューで重大な不整合がないことを確認した後、三点セットとレビュー済みの実装コードをもとに、`implementation_design_contract.md` を作成する。

実装設計契約には、少なくとも次を含める。

- 参照した仕様文書とコード。
- 仕様項目と実装箇所の対応。
- クラス、モジュール、関数、テストの責務。
- 入力検証、状態遷移、業務ルール、エラー処理の実装対応。
- コードだけでは復元しにくい仕様根拠。
- 参照画像、外部参照資産、手動確認対象。
- 既知差分、未テスト項目、残リスク。

## 12. アプリ設計書を作成する

`implementation_design_contract.md` 作成後、三点セット、実装設計契約、レビュー済みの実装コードをもとに、`app_design.md` を作成する。

アプリ設計書には、少なくとも次を含める。

- アプリの目的とスコープ。
- 参照した仕様文書、実装設計契約、コード、参照資産。
- 画面、操作、データ、業務ルールの設計。
- モジュール構成と責務。
- エラー処理。
- テスト方針と検証状況。
- ビルド、実行、運用上の注意。
- 既知差分、未テスト項目、残リスク。

三点セット、実装設計契約、コードの間に矛盾がある場合は、設計書へ断定的に取り込まず、不整合として列挙する。

## 13. アプリ設計書レビュー

`app_design.md` 作成後、三点セット、`implementation_design_contract.md`、レビュー済みの実装コードを正しく反映しているか確認する。

確認する内容:

- 三点セットの内容が `app_design.md` に反映されていること。
- `implementation_design_contract.md` の内容が `app_design.md` に反映されていること。
- 実装コードの構成、責務、主要処理が `app_design.md` に反映されていること。
- 参照画像、外部参照資産、既知差分、未テスト項目が落ちていないこと。
- 確定仕様、実装上の既知差分、残リスクが混同されていないこと。

このレビューだけで `app_design.md` やコードを修正しない。
問題があれば、原因に応じて上流文書または実装へ戻す。

## 14. 運用判断

次の条件を満たす場合、対象プロジェクトで許可された運用段階へ進める。

- ビルドが成功していること。
- 自動テストが成功していること。
- 必要な手動確認が完了していること。
- `README.md` にビルド、テスト、起動、手動確認の手順があること。
- `implementation_design_contract.md` と `app_design.md` に運用段階と残リスクが記録されていること。

利用者配布を伴う本番運用は、次を確定するまで開始しない。

- 配布形式
- 対象 OS または対象実行環境
- 必要なランタイム、依存関係、ライセンス条件
- 起動手順
- 手動確認結果

## 15. コンテキスト保存

作業終了時は、対象プロジェクトの再開メモに次を保存する。
対象アプリ用ディレクトリに `NEXT.md` がある場合は、その `NEXT.md` を使う。
ない場合は、対象プロジェクトの運用に従って再開メモを作成または更新する。

- 現在の運用段階
- 主要成果物
- 実装概要
- 検証状況
- 仕様変更時の反映順
- 未完了事項

再開メモは次回再開用の要点だけを書く。
長い残作業、詳細な問題点、保留事項は `backlog.md` などに分離する。

## 16. コミット前確認

コミット前に次を確認する。

- 生成物のビルドディレクトリ、キャッシュ、ログ、一時ファイルをコミット対象に含めていないこと。
- 今回の作業範囲外の未追跡ファイルを混ぜていないこと。
- `git diff --cached --name-status` で対象ファイルを確認していること。
- `NEXT.md` が次回再開に必要な内容を含んでいること。

## 17. コミット

コミットメッセージは、追加または変更した成果物と作業内容が分かる内容にする。

例:

```sh
git add NEXT.md docs/post_generation_workflow.md <target-app-dir>
git commit -m "コード生成後の成果物を追加"
```

生成物を除外する必要がある場合は、コミット前にステージ対象を明示的に確認する。
