# Qt Creator MCP のユースケース

このメモは、Qt Creator MCP を icpp 関連の検証で使った結果から、Qt Creator MCP の価値が強い用途と現時点で向かない用途を整理したものです。

## 中心的な用途

### Qt Creator の Build Issues を Codex が読み、修正に使う

Qt Creator でビルドし、`list_issues` で Build Issues のエラー位置と診断内容を取得します。
Codex はその情報をもとに該当ファイルを修正し、再ビルドして確認します。

この用途が、今回確認できた中心的な価値です。
Qt Creator が実際に使っている Kit、CMake 設定、ビルドディレクトリ、環境で出たエラーを、そのまま Codex の修正作業につなげられます。

## 補助的な機能

中心的な用途を支える補助機能として、次の操作も使えます。

- 現在のアクティブプロジェクトを確認する
- 現在のビルド構成を確認する
- Qt Creator 側のビルドを実行する
- Qt Creator で開いているファイルを読む

ただし、これらは単体では Qt Creator MCP 固有の強い価値ではありません。
Build Issues を Codex の修正作業につなげるための補助機能と考えるのが自然です。

## 現時点で向かない用途

### 1. QML の実行時エラー監視

今回の確認では、QML 実行時エラーは `list_issues` で取得できませんでした。

Application Output に出る種類のエラーは、現状の MCP 経由では扱いにくいです。

### 2. 実行中アプリのログ監視

ビルドエラーは取れますが、標準出力・標準エラー・Qt のログを継続的に読む用途には向きません。

### 3. `list_issues` を完全な現在状態として信頼する使い方

古いエラーが残ることがあったため、`list_issues` の結果だけで「まだ失敗している」と判断するのは危険です。

ビルド結果、対象ファイルのパス、現在のプロジェクトを合わせて見る必要があります。

### 4. Qt Creator 側の未保存バッファを前提にした修正

Codex は基本的にファイルを編集します。
Qt Creator 側で未保存の変更があると、ディスク上の内容とずれる可能性があります。

### 5. 完全自動の GUI 操作テスト

MCP でビルドやファイル操作はできますが、ウィンドウをクリックする、表示を目視確認するといった GUI テストそのものには向きません。

### 6. Qt Creator の全機能を外部から操作する用途

MCP で使える操作は限定されています。
プロジェクト設定、Kit 選択、Configure Project などは手動操作が必要になる場面があります。

## 記事向けのまとめ

Qt Creator MCP の中心的な価値は、Qt Creator の Build Issues を Codex が読めることにあります。
これにより、Qt Creator が実際に使っている Kit、CMake 設定、ビルド環境で発生したエラーを、そのまま Codex の修正作業につなげられます。

ファイル編集やリファクタリングは Codex だけでもできます。
そのため、MCP の価値は「Qt Creator のビルド診断を Codex に渡せること」に絞って考えるのがよいです。

一方で、QML の実行時ログや Application Output の監視、GUI の目視確認、Qt Creator の細かい設定操作までは担当しません。
現時点では、Qt Creator を操作する万能リモコンではなく、Build Issues を Codex に渡す接続口として使うのが現実的です。
