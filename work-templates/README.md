# 作業テンプレート

このディレクトリーには、新しい作業やプロジェクトを始めるときに使う文書テンプレートを置いています。
作業の再開に必要な情報、長期の残作業、設計判断を分けて管理し、`NEXT.md` の肥大化や重要な判断の消失を防ぐことが目的です。
作業するホスト、開発環境、AIセッションが変わっても、リポジトリー内の情報から作業コンテキストを復元できる状態を目指します。

## この構成の背景

この3ファイル構成とファイル名は独自のものですが、役割分担は既存の運用を小規模・個人プロジェクト向けに軽量化したものです。

| このテンプレート | 近い既存事例 |
|---|---|
| `NEXT.md` | Cline Memory Bankの `activeContext.md`。現在の作業、最近の変更、次の作業を記録する |
| `DECISIONS.md` | Architecture Decision Record（ADR）とdecision log。判断内容、理由、選択肢、制約を記録する |
| `backlog.md` | GitHub Issues／Projectsのbacklog。直近では扱わない残作業や保留事項を管理する |

参考資料:

- [Cline Memory Bank](https://cline.bot/blog/memory-bank-how-to-make-cline-an-ai-agent-that-never-forgets)
- [Architectural Decision Records](https://adr.github.io/)
- [GitHub Projects Quickstart](https://docs.github.com/en/issues/planning-and-tracking-with-projects/learning-about-projects/quickstart-for-projects)

このテンプレートでは、外部サービスや多数の文書を前提にせず、Gitで管理できる3つのMarkdownへ集約します。`DECISIONS.md` が大きくなった場合は一判断一ファイルのADRへ、`backlog.md` の更新頻度や件数が増えた場合はGitHub Issues／Projectsなどへ移行できます。
AIはこの仕組みを更新・利用する主体の一つです。人による作業引き継ぎ、PC移行、リモート環境、異なるAIツールへの切り替えにも同じ文書を使えます。

## ファイルの役割

| ファイル | 役割 |
|---|---|
| `AGENTS.next.md` | 複数プロジェクトで共有する `NEXT.md` の共通運用ルール。ホームディレクトリーへ配置する |
| `NEXT.md` | 現在の状態、次にやること、次回再開に必要な注意を書く |
| `DECISIONS.md` | 採用・不採用の設計判断と理由、未決論点、判断基準、継続する仕様・運用制約を書く |
| `backlog.md` | 次回すぐには着手しない長期の残作業、問題点、保留事項を書く |

## 新しい作業で使い始める

最初に、共通運用ルールをホームディレクトリーへ配置します。

```sh
cp /Users/sugita/Sites/work-templates/AGENTS.next.md ~/AGENTS.next.md
```

次に、対象ディレクトリーへ次の3ファイルをコピーします。

```sh
cp /Users/sugita/Sites/work-templates/NEXT.md .
cp /Users/sugita/Sites/work-templates/DECISIONS.md .
cp /Users/sugita/Sites/work-templates/backlog.md .
```

コピー後は、`NEXT.md`、`DECISIONS.md`、`backlog.md` の説明用項目を実際の内容へ置き換えます。該当する情報がない項目は、説明用項目を残さず `- なし` と書きます。`NEXT.md` を読む、または更新するときは、冒頭の指示に従って `~/AGENTS.next.md` を先に参照します。

## ホストをまたいで再開するための注意

- 3つの作業管理ファイルはGitで追跡し、別ホストから取得できる状態にする。
- `AGENTS.next.md` は各ホストのホームディレクトリーへ同じ内容で配置する。
- 関連ファイルは可能な限りリポジトリー相対パスで記載し、個人環境の絶対パスへ依存しない。
- 再開に必要なブランチ、基準コミット、ツールバージョン、外部依存、環境条件がある場合は `NEXT.md` に記載する。
- 未コミット変更がある場合は、その存在と扱いを `NEXT.md` に記載する。必要な変更本体はコミット、patchなど、別ホストへ移せる方法で保存する。
- 会話履歴にしか存在しない設計判断や制約を残さず、`DECISIONS.md` に記載する。
- 認証情報や秘密情報は作業管理ファイルへ記載しない。

## 情報の分け方

### NEXT.md に書くもの

- 作業の目的と現在の状態
- 次回最初に行う1つか2つの作業
- 次回の作業判断に直接必要な未完了事項
- 次回触るファイル
- 直近の注意事項と参照先

日付付きの作業記録に対する期間の目安は、直近5実作業日以内、または現在の作業テーマが完了するまでです。この期間制限を、現在も有効な設計判断や運用制約の削除理由には使いません。

### DECISIONS.md に書くもの

- 採用した方針と、その理由
- 採用しなかった案と、その理由
- まだ決めていない設計上の論点
- 判断時に優先する基準
- 今後も有効な仕様と運用制約

単に着手時期を先送りしている作業は、未決の設計判断ではなく `backlog.md` に書きます。

### backlog.md に書くもの

- 次回すぐには着手しない長期の残作業
- 現在分かっている問題と影響範囲
- 保留理由と再検討条件がある項目

完了履歴、検証ログ、設計判断の保管場所にはしません。

## 作業後に更新する

Codex に `NEXT.md` を現在の作業状態に合わせて更新するよう依頼します。
`NEXT.md` の冒頭から参照される `~/AGENTS.next.md` が、`DECISIONS.md` と `backlog.md` も読み込み、Git の差分、直近のコミット、関連文書を確認したうえで3つのファイルを必要に応じて更新する手順を定めます。

通常の更新では、次の流れになります。

1. 完了した作業をソース、README、CHANGELOG、Git コミットなどへ反映する。
2. 現在の状態と直近の作業を `NEXT.md` に反映する。
3. 新しい設計判断があれば `DECISIONS.md` に反映する。
4. 直近の対象から外れた残作業や保留事項を `backlog.md` に移す。
5. 差分と参照関係を確認し、可能なら `git diff --check` を実行する。

## 大きく整理するとき

セクション単位の削除、複数の独立項目の削除、設計判断や不採用理由の削除、大幅な再構成は、通常の更新として自動実行しません。
まず、残す項目、移動する項目、削除候補、理由、移動先を提示させ、内容を確認してから反映を指示します。

整理を検討する場合は、次のように指示します。

```text
NEXT.md、DECISIONS.md、backlog.md の整理案を作ってください。
まだファイルは変更せず、残す項目、移動する項目、削除候補と根拠を示してください。
```

## 完了履歴の扱い

完了した作業の長い記録や検証ログを、作業管理ファイルへ蓄積し続ける必要はありません。ただし、削除前に同じ情報が次のいずれかで確認できることを確かめます。

- `CHANGELOG.md`
- `README.md` や利用者向けガイド
- 検証記録
- 特定できるGitコミット

今後の判断に影響する結論、理由、制約は完了履歴として削除せず、`DECISIONS.md` へ残します。
