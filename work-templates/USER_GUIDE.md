# 作業コンテキスト管理利用ガイド

## 1. 使用目的

この仕組みは、作業中に生じるコンテキストを役割別の Markdown ファイルに整理し、人間と AI が継続して利用できる状態で保存するためのものです。

主な目的は次のとおりです。

- AI の会話履歴などに保存するコンテキストの増大を防ぐ
- 作業の経緯、判断理由、仕様、制約などの大事なコンテキストを恒久保存する
- 異なるホスト、開発環境、AI セッションの間でコンテキストを共有する
- 作業再開時の読み込み量と確認時間を減らす
- 現在の作業、長期課題、継続する判断を分離し、必要な情報を見つけやすくする
- 作業の中断、担当者の交代、AI ツールの変更があっても作業を継続できるようにする
- 設計判断や不採用理由を残し、同じ調査や議論の繰り返しを防ぐ
- Git で変更経緯を追跡し、古い情報を安全に整理できるようにする

## 2. 忙しい方向け：この3つだけ押さえる

### 2.1 最初にすること

`work-templates.zip` を展開し、共通運用ルールと作業管理用ファイルを配置します。

- `AGENTS.next.md` を各ホストの `~/AGENTS.next.md` に配置する
- 次の3ファイルを対象プロジェクトに配置する
  - `NEXT.md`
  - `backlog.md`
  - `DECISIONS.md`

`work-templates.zip` には `README.md`、`AGENTS.next.md` と上記3つのテンプレートが含まれます。この利用ガイドの Markdown と PDF は ZIP に含まれず、配布ページから別途参照します。

作業管理用ファイルがすでに配置されている場合、テンプレートで上書きする必要はありません。

### 2.2 作業完了時にすること

AI に `NEXT.md` を現在の作業状態に合わせて更新するよう依頼します。

### 2.3 作業再開時にすること

AI に `NEXT.md` を読んでもらい、作業を再開します。

`NEXT.md` の冒頭から `~/AGENTS.next.md` の共通運用ルールが参照され、AI は `backlog.md` と `DECISIONS.md` も読み込みます。

## 3. 仕組みの全体像

この仕組みは、1つの共通運用ルールと3つの情報保存先で構成されます。

| ファイル | 役割 |
|---|---|
| `AGENTS.next.md` | 複数プロジェクトで共有する `NEXT.md` の共通運用ルールを定める |
| `NEXT.md` | 現在の状態、次にやること、次回再開に必要な情報を保存する |
| `backlog.md` | 次回すぐには着手しない残作業、問題点、保留事項を保存する |
| `DECISIONS.md` | 今後も有効な判断、その理由、仕様、判断基準、運用制約を保存する |

`work-templates.zip` には、`README.md`、`AGENTS.next.md`、`NEXT.md`、`backlog.md`、`DECISIONS.md` が含まれます。利用ガイドは配布ページから Markdown または PDF で別途参照します。

配布物の `AGENTS.next.md` を各ホストのホームディレクトリーへ `~/AGENTS.next.md` として配置します。`NEXT.md` は、このファイルを明示的に読むよう指示します。存在しない場合は作業管理ファイルを整理・削除せず、利用者へ確認する構成です。

対象プロジェクトの3ファイルをプロジェクトと一緒に Git で管理し、各ホストの `~/AGENTS.next.md` を同じ内容にすると、ホストや AI セッションが変わっても同じコンテキストと運用ルールを利用できます。

## 4. 情報の振り分け方

保存先に迷った場合は、次の順序で判断します。

1. 次回の作業再開に直接必要なら `NEXT.md` に書く。
2. 次回すぐには着手しない作業、問題点、保留事項なら `backlog.md` に書く。
3. 今後の判断に影響する結論、理由、仕様、制約なら `DECISIONS.md` に書く。
4. 完了履歴や長い検証ログは、`CHANGELOG.md`、`README.md`、検証記録、または特定できる Git コミットに残す。

短く言い換えると、次のようになります。

- 次回必要なら `NEXT.md`
- 後で取り組む作業なら `backlog.md`
- 今後も効く判断なら `DECISIONS.md`

同じ内容を複数のファイルへ詳しく重複して書く必要はありません。正本となるファイルを1つ決め、ほかのファイルから相対パスや見出し名で参照します。

## 5. `NEXT.md` の使い方

### 5.1 役割

`NEXT.md` は、次回の作業再開に直接必要な情報を保存するファイルです。作業履歴の保管庫ではなく、現在地と次の一手を短時間で把握するために使います。配布されたテンプレートをコピーした後、説明用の項目を次回再開に必要な最小限の情報へ置き換えます。

冒頭には `~/AGENTS.next.md` を先に読む指示と、ファイルが存在しない場合の保護ルールを置きます。この冒頭のルールは、ユーザーから明示的な指示がない限り変更しません。

### 5.2 更新するタイミング

- 作業の目的や状態が変わったとき
- 次にやることが変わったとき
- 作業を中断するとき
- 作業テーマを完了したとき
- 再開に必要な注意や参照先が増えたとき

### 5.3 各セクションの書き方

#### 現在の状態

作業の目的、完了した範囲、残っている範囲、現在の位置づけを書きます。詳細な作業履歴や検証ログは、次回の判断に必要な範囲だけに絞ります。

#### 次にやること

次回最初に行う作業を書きます。原則として1つか2つに絞り、着手できる具体的な表現にします。複数テーマがある場合も、各テーマの次の一手だけを書きます。

#### 未完了

次回の作業判断に必要な未完了だけを書きます。長期の残作業や詳しい問題点は `backlog.md`、今後も有効な判断や運用制約は `DECISIONS.md` に移します。

#### 触るファイル

次回変更する予定のファイルと、そのファイルを触る理由を、可能な限りリポジトリー相対パスで書きます。

#### 注意

次回すぐに思い出す必要がある制約、事故防止、承認待ち、壊しやすい点、環境条件、未コミット変更の扱いなどを書きます。

#### 関連ファイル

再開時に参照するファイルと役割を書きます。`DECISIONS.md` は継続する判断、仕様、運用制約、`backlog.md` は次回すぐには着手しない残作業、問題点、保留事項の参照先です。必要に応じて該当見出しも示します。

### 5.4 コンパクトに保つ方法

日付付きの作業記録は、直近5実作業日以内、または現在の作業テーマが完了するまでを目安にします。実作業日とは、実際に作業、判断、検証、コミットを行った日です。

この期間は作業履歴を整理する目安であり、現在も有効な仕様、判断、不採用理由、運用制約を削除する理由にはなりません。それらは `DECISIONS.md` に残します。

### 5.5 記入例

```markdown
## 現在の状態

- 検索画面の表示実装は完了した
- キーボード操作の検証が残っている

## 次にやること

- 検索結果一覧のキーボード操作を検証する

## 未完了

- 長期課題は `backlog.md` の「検索速度の改善」を参照

## 触るファイル

- `src/search-view.js`
- `tests/search-view.test.js`

## 注意

- 既存の検索 URL は変更しない

## 関連ファイル

- `DECISIONS.md` の「検索 URL を維持する」
```

## 6. `backlog.md` の使い方

### 6.1 役割

`backlog.md` は、次回すぐには着手しない長期の残作業、問題点、保留事項を保存するファイルです。現在の作業状態や完了履歴は保存しません。

### 6.2 残作業

実施する必要があるが、直近の作業対象ではないものを書きます。作業内容だけでなく、必要性または完了条件と、関連ファイルや参照先も残します。

### 6.3 問題点

現在分かっている問題、影響範囲、調査結果や再現条件の参照先を書きます。次回すぐに解決する問題は `NEXT.md` に置きます。

### 6.4 保留事項

保留している内容、保留理由、再検討する条件を書きます。単に着手時期を先送りしている作業も、未決の設計判断ではなくこちらに置きます。

### 6.5 `NEXT.md` に戻すとき

次に着手する項目が決まったら、その項目の実施に直接必要な情報を `NEXT.md` へ移します。詳しい調査記録などが引き続き必要なら、`backlog.md` に残して `NEXT.md` から参照します。

### 6.6 記入例

```markdown
## 残作業

### 1. 検索速度の改善

- 大量データでの検索時間を短縮する
- 1万件のデータで応答時間が1秒以内になれば完了
- 関連: `src/search-index.js`

## 保留事項

### 1. 外部検索サービスの導入

- 現時点では導入しない
- 運用費が確定していないため保留
- 月間検索件数が10万件を超えた場合に再検討する
```

## 7. `DECISIONS.md` の使い方

### 7.1 役割

`DECISIONS.md` は、今後の作業でも有効な判断と、その判断に必要なコンテキストを保存するファイルです。方針だけでなく理由も残すことで、同じ議論の繰り返しを防ぎます。

### 7.2 採用済み

採用した方針と、その理由を書きます。判断に関係した制約や優先事項があれば一緒に残します。

### 7.3 不採用

検討した案、不採用理由、再検討する条件を書きます。不採用理由を残すと、前提が変わっていないのに同じ案を再検討することを防げます。

### 7.4 まだ決めていないこと

実装作業ではなく、判断が必要な未決事項を書きます。何を確認して決めるかも残します。着手時期だけを保留している作業は `backlog.md` に書きます。

### 7.5 判断基準

複数の案を比較するときに何を優先するかを書きます。たとえば、既存 URL の維持、互換性、保守性、運用コストなどです。

### 7.6 継続する仕様・運用制約

今後の変更でも維持する仕様と、作業時に守る運用制約を書きます。理由も残すと、制約がまだ必要かを後から判断できます。

### 7.7 方針を変更するとき

古い方針を理由なく消さず、新しい判断、変更理由、変更日または関連コミット、古い方針の扱いを記録します。経緯を詳しく残す必要がある場合は、一判断一ファイルの ADR への移行も検討します。

### 7.8 記入例

```markdown
## 採用済み

### 1. 既存の検索 URL を維持する

- `/search` を引き続き使用する
- 外部サイトからのリンクと利用者のブックマークを壊さないため

## 不採用

### 1. 検索画面を別ドメインへ移す

- 運用を分離する案を検討した
- 認証と監視が複雑になるため採用しない
- 検索負荷を現在の構成で処理できなくなった場合に再検討する
```

## 8. 基本的な運用の流れ

### 8.1 作業を開始するとき

初めて利用するホストでは、`work-templates.zip` を展開し、同梱の `AGENTS.next.md` を `~/AGENTS.next.md` として配置します。対象プロジェクトには3つの作業管理ファイルを配置します。既存の作業情報がある場合は、第4章の基準に従って3つの保存先へ整理します。

### 8.2 作業中

次の作業が変わった場合は `NEXT.md`、長期課題が見つかった場合は `backlog.md`、継続する判断が生じた場合は `DECISIONS.md` を更新します。会話履歴だけに重要な判断を残さないようにします。

### 8.3 作業を中断するとき

AI に `NEXT.md` の更新を依頼します。共通運用ルールにより残りの2ファイルも必要に応じて更新され、次回最初に行う作業と注意事項が `NEXT.md` だけで把握できる状態になります。

### 8.4 作業を再開するとき

AI に `NEXT.md` を読んでもらいます。AI は `NEXT.md` 冒頭の指示に従って `~/AGENTS.next.md` を先に確認し、残りの2ファイルも読み込みます。人が再開する場合も、最初に `NEXT.md` を読み、必要なときだけ残りの2ファイルを参照します。

### 8.5 作業を完了するとき

AI に `NEXT.md` の更新を依頼します。詳しい確認事項は第9章に従います。

## 9. 作業完了時の更新

### 9.1 完了内容を確認する

Git の差分、直近のコミット、関連文書、検証結果を確認し、何が完了して何が残ったかを確定します。

### 9.2 3つのファイルを整理する

- `NEXT.md` から完了した一時的な項目を整理し、次の作業状態を記載する
- 残った長期課題、問題点、保留事項を `backlog.md` に保存する
- 作業中に決まった方針、理由、仕様、制約を `DECISIONS.md` に保存する

### 9.3 完了履歴と検証結果を保存する

完了履歴や長い検証ログは、次のいずれかで追跡できる状態にします。

- `CHANGELOG.md`
- `README.md` や利用者向けガイド
- 専用の検証記録
- 特定できる Git コミット

今後の判断に影響する結論、理由、制約は、完了履歴として消さず `DECISIONS.md` に保存します。

### 9.4 差分を確認する

更新後に Git の差分を確認します。可能であれば `git diff --check` も実行し、空白エラーなどがないことを確認します。

### 9.5 Git へ記録する

作業内容と作業管理ファイルを一緒に追跡できるようにします。別ホストで再開する場合は、必要なコミットや変更を共有リポジトリーなど、そのホストから取得できる場所へ反映します。

## 10. `AGENTS.next.md` による更新手順

### 10.1 役割

`AGENTS.next.md` は、`NEXT.md` を入口として、AI が3つの作業管理ファイルを読み込み、現在の作業状態に合わせて更新するための共通手順を定めます。

### 10.2 使用するタイミング

- 作業を中断するとき
- 作業テーマが変わったとき
- 作業を完了したとき
- 3つのファイルを現在の状態に合わせて整理するとき

### 10.3 AI への依頼方法

対象プロジェクトの作業環境で、AI に「`NEXT.md` を現在の作業状態に合わせて更新してください」と依頼します。AI は `NEXT.md` 冒頭の指示から `~/AGENTS.next.md` を読み、Git の差分、直近のコミット、3つの作業管理ファイル、関連文書を確認します。`backlog.md` と `DECISIONS.md` を依頼文に列挙する必要はありません。

### 10.4 通常更新と事前確認

情報の追記、項目の移動、現在の状態への修正などは通常更新として実施します。

次の変更が必要な場合、共通運用ルールは AI にまだ変更せず確認を求めるよう指示します。

- セクション単位の削除
- 複数の独立項目の削除
- 設計判断や不採用理由の削除
- 大幅な再構成

AI が示した対象、理由、移動先を確認してから、実施するかを指示します。

### 10.5 更新後の報告

AI から、`NEXT.md`、`backlog.md`、`DECISIONS.md` の変更内容と、差分確認などの検証結果をファイル別に受け取ります。

## 11. 安全に整理するためのルール

- 情報を日付、行数、古さだけを理由に削除しない
- 削除前に、今後の判断へ影響する結論、理由、制約の保存先を確認する
- 完了履歴や検証ログは、同じ情報が追跡可能な文書または Git コミットに残っている場合に限り整理する
- セクション単位の削除、複数項目の削除、重要な判断の削除、大幅な再構成は事前に確認する
- 既存の未コミット変更を保護し、無関係なファイルを変更しない
- 認証情報、秘密情報、公開すべきでない個人情報を書かない
- ホスト固有の絶対パスは避け、可能な限りリポジトリー相対パスを使う

## 12. 異なるホスト間で共有する方法

3つの作業管理ファイルを Git で追跡し、別ホストから取得できる状態にします。

共通運用ルールは、ZIP に同梱された `AGENTS.next.md` を各ホストの `~/AGENTS.next.md` へ同じ内容で配置して共有します。更新した場合は、使用するすべてのホストへ反映します。

作業を終了するときは、再開に必要なブランチ、基準コミット、ツールのバージョン、外部依存、環境条件を必要に応じて `NEXT.md` に書きます。未コミット変更がある場合は、その存在と扱いも記載し、変更本体はコミットや patch など別ホストへ移せる方法で保存します。

別ホストで再開するときは、`~/AGENTS.next.md` が配置されていることを確認します。ローカルの未コミット変更や競合の可能性を確認してから最新状態を取得し、その後、AI に `NEXT.md` を読んでもらいます。共通運用ルールにより残りの2ファイルも読み込まれます。

## 13. 運用例

### 13.1 作業を途中で中断する

1. AI に `NEXT.md` の更新を依頼する。
2. `NEXT.md` に現在地と次の一手が記載されたことを確認する。
3. 新しい長期課題や判断が、適切なファイルへ保存されたことを確認する。
4. 必要な変更を Git で追跡できる状態にする。

### 13.2 長期課題が見つかる

現在の作業では対応しない課題を `backlog.md` に追加します。その課題が次の作業対象になったら、着手に必要な情報を `NEXT.md` へ移します。

### 13.3 設計方針を決定する

採用した方針と理由を `DECISIONS.md` に書きます。次回の作業にも直接影響する場合は、`NEXT.md` から該当する判断を参照します。

### 13.4 作業テーマを完了する

1. 完了結果をソース、利用者向け文書、検証記録、Git コミットなどへ残す。
2. AI に `NEXT.md` の更新を依頼する。
3. 残作業が `backlog.md`、継続する判断が `DECISIONS.md` に保存されたことを確認する。
4. `NEXT.md` を次の作業テーマに合わせる。

### 13.5 別ホストで再開する

1. 必要な変更を共有元から取得する。
2. AI に `NEXT.md` を読んでもらう。残りの2ファイルは共通運用ルールにより読み込まれる。
3. `NEXT.md` の「次にやること」から作業を再開する。

## 14. よくある間違い

### `NEXT.md` にすべての履歴を残す

再開に必要な情報が埋もれます。完了履歴は追跡可能な文書や Git に残し、継続する判断は `DECISIONS.md` へ移します。

### 長期課題を `NEXT.md` に残し続ける

次回すぐには着手しない項目は `backlog.md` へ移します。

### 作業項目を `DECISIONS.md` に書く

実装時期を待つだけの作業は `backlog.md` に書きます。`DECISIONS.md` には判断が必要な論点や、決定した方針を書きます。

### 理由を残さず方針だけを書く

後から判断を評価できません。採用理由、不採用理由、再検討条件も残します。

### 保存先を確認せず完了項目を削除する

完了結果、判断、制約が失われる可能性があります。追跡可能な保存先を確認してから整理します。

### 同じ情報を複数のファイルへ詳しく書く

更新時に不整合が生じます。正本を決め、ほかのファイルから参照します。
