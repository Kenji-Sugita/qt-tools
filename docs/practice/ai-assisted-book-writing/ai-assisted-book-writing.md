# AI と協力して本を書く方法

本を書こうとする人が、AI とともに企画を考え、原稿を作り、確かめ、読者に届けるまでの進め方をまとめます。技術書の共同制作で得た経験をもとに、実用書、解説書、教材、創作にも応用できる形に整理しています。以下は、この経験から導いた実践方法です。

著者は、本で何を伝えるか、何を採用するか、どの状態で読者に届けるかを判断します。AI は、問いや別案を出し、資料を整理し、原稿と付属物を作り、矛盾や不足を探す役割を担います。やり取りの中で著者自身の考えが深まることも、協働の大切な成果です。

原稿を一度に生成して完成とするよりも、小さく作り、具体物を見て判断し、その判断を次の制作に反映する進め方が適しています。文章の完成度に加え、内容の確かさ、読者が理解できる順序、図や付属物との一致、配布した形式での読みやすさまで扱います。

## 著者と AI の役割

著者に必要なのは、すべての文章を自分で入力することよりも、本の目的と内容に継続して関わることです。AI が書いた箇所でも、その意味と根拠を確かめ、読者に伝える表現として引き受けられるかを判断します。理解や検証が追いつかない箇所は、調べ直す、詳しい人に確認する、扱う範囲を絞る、といった対応を取ります。

AI にも企画や判断の案を求めます。著者が思いつかなかった論点を示し、既存資料から見落としを探し、構成を比較する働きは、単純な文章生成とは異なる価値があります。ただし、AI がもっともらしく述べたことと、資料や実物で確認したことは区別します。

| 仕事 | 著者が担うこと | AI に任せられること |
| --- | --- | --- |
| 企画 | 読者、目的、立場、扱う範囲を決める | 読者の疑問、構成案、範囲の過不足を示す |
| 内容 | 経験、主張、説明したいことを示し、採否を判断する | 資料の比較、下書き、別案、反例を用意する |
| 編集 | 説明の深さ、順序、文体、残す表現を判断する | 重複、用語の揺れ、前提不足、参照のずれを探す |
| 検証 | 確認基準を決め、結果と残る限界を評価する | 実行可能な範囲で照合や試験を行い、記録を残す |
| 制作と公開 | 読者向けの完成度と公開範囲を判断する | 電子書籍、図、付属物、案内文の制作を支援する |

AI が使える資料、ファイル、実行環境、外部サービスは作業によって異なります。「調べた」「動かした」「表示を確認した」と報告されたら、何を使い、どの範囲を確認したのかも受け取ります。

## 最初に本の方針を決める

書き始める前に、読者と到達点を短い文章にします。「初心者向け」の一言では、何を知っている人が、読後に何をできるようになるのかが曖昧です。読者が読む前と読んだ後の違いを説明できる程度に具体化します。

方針には、次の内容を含めます。

- 想定する読者と、読む前に必要な知識や経験。
- 本を通して理解してほしいこと、できるようになってほしいこと。
- 扱う主題と、今回は扱わない範囲。
- 本の使い方。通読、自習、参照、物語を楽しむことなど。
- 分量の目安、章の書き方、文体、配布形式。
- 根拠となる資料、対象時点や版、検証する環境。
- 著者の確認が必要な判断と、AI がそのまま進めてよい作業。

章数や分量は最初の目安です。必要な説明が増えた場合は、到達点と読者の負担に照らして見直します。増やすたびに、既存章へ統合するのか、独立した章にするのか、本の範囲を広げるのかを判断します。

合意した内容は、会話だけに置かず、執筆方針としてファイルに保存します。AI への依頼文を兼ねても構いませんが、人が読んでも現在の方針が分かる書き方にします。古い条件と新しい条件が並んでいる場合は、現在の条件を明示します。

## 既存の資料から本の骨格を作る

著者の講演資料、講義ノート、記事、実務記録、メモには、その人が何を大切にしてきたかが表れます。AI に整理を依頼するときは、元資料の見出しだけでなく、説明の中身や具体例まで照合させます。

資料と章の対応表を作ると、説明済みの内容、説明が薄い内容、未収録の内容を分けられます。スライドで口頭説明を前提にしていた箇所は、本だけで理解できる説明に補います。非表示スライドや補足資料も対象にする場合は、確認範囲を明示します。

目次は、読者が何を学び、何を探すための章なのかが分かる表現にします。内容が増えて見通しが悪くなったら、主題や用途でカテゴリーを作ります。難易度、用途、時系列のどれで整理するかは、本の使い方に合わせて選びます。

学習する順序と、探しやすい分類が一致しないこともあります。その場合は、分類を保ちながら、先に読む章を示します。「理解に必須の前提」と「併せて読むと役立つ内容」を分けると、読者は必要な寄り道を判断できます。

## 一章を作ってから全体へ広げる

最初に代表的な一章を作り、説明の深さや文体を著者が確かめます。技術書なら、目的、必要なファイル、動く例、実行手順、期待する結果、理由と注意点までそろえます。実用書なら、読者が置かれる状況、具体的な手順、判断の理由、適用できない条件まで書きます。

一章がよくても、全体がうまくいくとは限りません。次に性質の異なる数章を作り、説明の型が合うかを見ます。基本概念の章、手順の章、比較の章などを同じ型に押し込むと、不自然な反復や説明不足が生じます。共通に必要な項目と、章ごとに変えてよい部分を分けます。

その後、章やカテゴリーなど、内容を判断できる単位で執筆を進めます。AI が大きな原稿を作れる場合でも、読者と著者が確認できる単位を保つと、方針のずれを途中で直せます。

## レビューと改訂を繰り返す

レビューでは、評価する対象と観点を具体的にします。「よい本ですか」と尋ねるだけでは、何を根拠に、どこまで確認したのかが分かりにくくなります。

| 観点 | 確認すること |
| --- | --- |
| 範囲 | 到達点に必要な内容がそろい、似た章が重複していないか |
| 順序 | 未説明の知識を前提にしていないか。前提章に循環がないか |
| 深さ | 用語の紹介にとどまらず、理由、選択条件、失敗への対処を説明しているか |
| 整合 | 本文、図、手順、サンプル、章への参照が一致しているか |
| 確かさ | 事実、実測、著者の見解、推測、未確認事項を混同していないか |
| 文章 | 読者に必要な説明が自然につながり、定型句や反復が読みを妨げていないか |
| 読者の体験 | 本と付属物を受け取った人が、意図した読み方や作業を進められるか |

指摘には、対象箇所、困る理由、修正案、根拠を付けさせます。著者はそれを見て、採用、修正して採用、保留、不採用を判断します。AI の提案が本の範囲を広げる場合は、当初の目的との関係を確認します。

「レビュー」と「修正」は依頼の中でも区別します。レビューだけを求めたときに原稿を変更しない、修正を任せたときは対象と結果を報告する、と決めておくと、著者の判断と原稿の状態がずれにくくなります。繰り返す修正は、対象と基準を合意してまとめて任せられます。

「問題がなくなるまで」を進め方にする場合も、終える条件を定めます。例えば、採用した指摘の修正、決めた検証の成功、未確認事項の記録までを一区切りとします。AI が新しい提案を出し続けることと、既知の不具合が残っていることを分け、提案をすべて実施することを完成条件にしないようにします。

## 本文と付属物を一緒に育てる

技術書では、本文が正しくても、掲載コードが欠けていたり、付属ファイルと違っていたりすると、読者は学習を進められません。実用書の記入用紙、教材のデータ、創作の地図や人物表も、本文と対応する別の成果物として扱います。

同じ情報を複数の場所に手入力するほど、改訂でずれが生じます。掲載コードは実行するファイルから取り込む、章と付属物の対応表を持つ、目次や章番号を一括生成する、といった方法で一致を保ちます。自動化しても、どの情報を正しいものとして扱うかは明確にします。

学習用の例は、読者が準備して実行できる状態まで用意します。変更前後を比較して説明する場合は、変更する箇所と結果を具体的に示します。単独で試すことを目的にした章なら、別の章からファイルを集めなくても実行できる構成にします。

共通の準備や対象環境は、冒頭や付属物の案内にまとめます。各章では、その章で異なる条件を説明します。同じ注意書きを機械的に繰り返すと、必要な説明が埋もれます。

## 内容と表示を別々に確かめる

検証は、何を確かめたかによって意味が違います。ファイルが存在すること、プログラムが起動すること、説明どおりに操作できること、読者の環境でも同じ結果になることは、それぞれ別の確認です。

| 確認の段階 | 確かめる内容 | 残す記録の例 |
| --- | --- | --- |
| 内容の照合 | 引用、数値、用語、掲載物が根拠や元データと一致する | 出典と箇所、対象版、照合結果 |
| 構造の確認 | 必須項目、章番号、参照先、目次がそろう | 対象数、検出した欠落や重複 |
| 実行や再現 | 手順、計算、コードが期待する結果を出す | 環境、入力、実行方法、結果 |
| 出力形式の確認 | 電子書籍や印刷物で文字、図、改ページが読める | 形式、閲覧アプリ、確認した箇所と画面 |
| 読者としての確認 | 説明と付属物だけで目的に到達できる | つまずいた箇所、必要だった補足、修正結果 |

文章ファイルにコードが入っていても、電子書籍では文字色やページ分割の設定で空白に見えることがあります。内容の照合が成功しても、配布形式での表示確認は別に必要です。明暗テーマ、画面幅、長いコードや表、画像の見え方など、その本で問題になりやすい条件を選びます。

図や画面例は、説明する実物から取得します。読みやすくするための加工では、原画を保存し、説明に必要な情報が変わっていないかを確かめます。概念図や想像図を使う場合は、実際の画面と取り違えない表現にします。

未確認の環境については、動作を想定していることと、実際に確認したことを書き分けます。また、文章や空白だけを変えた際の内容一致と、改めて実行した試験を同じ実績として数えないようにします。

## 著者の言葉として文章を整える

自然な文章にするには、本で何を伝えたいかを先に確かめます。著者の経験や判断を具体的に示し、抽象的な賛辞、同じ導入句、説明のたびに現れる結びを減らします。読者がすでに理解したことを繰り返すより、次に必要な理由や例を足します。

AI が短く整えた結果、条件や例外、著者が大切にしていた意味が落ちることもあります。推敲後は読みやすさと意味の両方を確かめます。「自然にして」という依頼でも、事実、結論、確信の強さまで変えないように指定します。

著者が実際には行っていない経験を一人称で加えたり、確かめていない人物の発言を作ったりしてはいけません。経験として書く部分には著者の経験を使い、説明のための架空例は架空例として扱います。

## 長い制作を続けられる記録を残す

長い会話の中だけで本を管理すると、採用した条件や途中の判断を見失います。再開時に必要なのは、すべての会話の再現よりも、現在の方針、原稿、判断の理由、確認結果が分かる記録です。

| 記録 | 残す内容 |
| --- | --- |
| 執筆方針 | 読者、到達点、範囲、文体、章の共通項目、制作上の制約 |
| 構成と対応 | 章の目的、前提、関連章、資料や付属物との関係 |
| 判断の記録 | 採用した案、理由、変更してはいけない事項 |
| 次の作業 | 現在の状態、次に進める内容、再開時の注意 |
| 残る課題 | 未確認事項、後で扱う内容、公開後に改訂する項目 |
| 検証の記録 | 対象の版、環境、方法、結果、確認していない範囲 |

ファイル名は作業に合わせて決めます。例えば、執筆方針を `prompt.md`、再開用の情報を `NEXT.md`、判断を `DECISIONS.md`、残る課題を `backlog.md` に分ける方法があります。小さな本なら一つの管理文書から始めても構いません。

原稿や付属物は版を管理し、大きな変更の前後を比較できるようにします。AI に修正を任せるときは、対象外のファイルや著者が確定した表現を伝えます。章を移した場合は、本文だけでなく参照、付属物、図、目次への影響も確認します。

## 公開する版を整える

公開する際は、原稿、電子書籍、付属物、紹介文が同じ版の内容を説明しているかを照合します。表紙、著者名、発行者名、版表示、対象読者、確認環境も合わせます。内部の作業記録と、読者に渡す付属物は分けます。

プレビュー版では、読者に役立つ内容と、確認や改訂が残る範囲を説明します。確認済みのように見せて公開することも、未完成という言葉だけで何も伝えないことも避け、どこまで使える版なのかを具体的に示します。

AI に原稿や配布物の作成を依頼することと、外部へ公開することは別の作業です。アップロード、申し込みページの作成、サイト掲載などは、使うサービスと依頼範囲に応じて扱います。すでに任された作業の許可を繰り返し求める必要はありませんが、原稿作成の依頼だけで公開まで任されたと解釈しないようにします。

引用元や画像・データの利用条件、著者や発行者の表記、AI の利用に関する説明は、扱う素材と配布先に合わせて整理します。AI には出典や確認事項の一覧を作らせ、著者が実際の素材と照合できる状態にします。

## 最初の依頼に使える例

次の例の角括弧を埋めると、企画と制作の基準を伝えられます。まだ決められない項目は、AI に案と選択理由を求めます。

> [主題]について、[想定する読者]に向けた本を一緒に作ります。読者が読み終えたときに[到達点]を得られることを目指します。
>
> 元にする資料は[資料]です。私の経験や意見として使う箇所と、資料で確認する事実を区別してください。資料にない情報を補う場合は、根拠や仮定を示してください。
>
> まず目次案を作り、各章の目的、前提、扱う範囲を示してください。重複や不足も指摘してください。構成を決めたら代表的な一章を作り、私が説明の深さと文体を確認してから全体へ広げます。
>
> 執筆では[必要な例や付属物]を用意し、本文との一致を保ってください。レビューでは対象箇所、困る理由、修正案を示してください。内容の追加や方針変更は、[著者が判断する範囲]を守って進めてください。
>
> 確認は[環境と方法]で行い、確認できたことと残ることを記録してください。公開前には[配布形式]で実際に読み、図やコード、表、参照先も確かめます。保存先は[場所]です。

改訂を依頼するときは、次のように対象を絞れます。

> 今回は[対象の章や項目]を修正してください。[変更する点]を改善し、[保持する内容]は変えないでください。影響する本文・図・付属物もそろえ、修正した箇所と実施した確認、残る確認を報告してください。

## 本の種類に合わせて確認基準を変える

技術書では、実行できる例、対応する画面、確認した環境が大きな判断材料になります。実用書では、手順の成立条件や例外、読者が判断に迷う箇所を確認します。調査や解説の本では、主張と資料の関係、対象時点、反対の見方を落としていないかが重要です。

創作では、事実の正誤だけで判断できない部分が増えます。人物の動機、視点、時間の流れ、作品の語り口、あえて説明しないことを著者が決めます。AI は設定の矛盾や読者が迷う箇所を探せますが、意図した余白を一律に埋めないよう、作品ごとの基準を伝えます。

どの種類でも、AI との協働によって時間がどれだけ短くなるか、品質がどれだけ上がるかは、実際の制作を通して確かめます。初稿にかかった時間だけでなく、レビュー、確認、手戻りも含めて振り返ると、次に任せる仕事を判断しやすくなります。

## 共同制作で経験したことと応用する際の注意

この方法の出発点になった技術書の制作では、章項目を繰り返し見直し、既存のセミナー資料との比較から不足を補いました。内容が増えた後はカテゴリーで整理し、前提となる章と関連する章を示しました。独立したサンプルと変更例を整え、本文、図、付属物、電子書籍を対応させる作業も進めました。

一方で、項目の増加によって見通しが悪くなること、共通説明の繰り返しがくどくなること、本文のデータが正しくても電子書籍ではコードが見えにくくなることもありました。これらは、生成後に著者が具体物を見て指摘し、原因を調べて改訂する必要を示しています。

実行試験や照合の記録があっても、全章の著者確認、すべての閲覧環境や OS での確認が完了したことにはなりません。この制作経験からは、検証の対象と限界を残す手順を引き継げます。他の分野や本でも同じ成果が得られるという保証ではなく、それぞれの読者と内容に合わせて確認基準を作るための出発点です。
